# 018 — explorgdb vs GDAL 组件性能对比分析

> 日期: 2026-06-10
> 触发: 10M 数据集基准测试中，explorgdb 比 GDAL 组件快 8.2×

---

## 1. 基准数据

### 1.1 10M 数据集 (817 万结果, Large 场景)

| 路径 | 总耗时 | 加载 | 索引查询 | 记录获取 |
|------|-------:|-----:|--------:|--------:|
| **explorgdb (mmap)** | **1,366 ms** | 29.8ms | 656ms | 207ms (peek) + 185ms (bbox) |
| **GDAL component** | 10,923 ms | 0.6ms | 0.2ms | **10,922ms** |
| **加速比** | **8.0×** | — | — | **52.8×** |

### 1.2 小数据集 (2,390 要素, Large 场景, ~1800 结果)

| 路径 | 总耗时 | 加载 | 索引查询 | 记录获取 |
|------|-------:|-----:|--------:|--------:|
| **explorgdb** | **59 ms** | 0.3ms | 0.2ms | 58.6ms |
| **GDAL component** | 59 ms | 49ms | 0.6ms | 9.3ms |
| **加速比** | 1.0× | — | — | — |

小数据集两者持平（explorgdb 的加载开销抵消了获取优势），大数据集差距急剧拉大。

---

## 2. 性能差距的 4 个根因

### 根因 1: I/O 系统调用 — mmap vs pread

| 指标 | explorgdb | GDAL component |
|------|-----------|----------------|
| I/O 方式 | `mmap()` + `memcpy()` | `pread()` 每次读 4~140 字节 |
| Large_10M 系统调用次数 | **0 次** (mmap 一次映射) | **16.3M 次** (8.17M × 2 次 peek) |
| 单次 peek 耗时 | 0.025 μs | 1.34 μs |
| **每特征 I/O 差距** | — | **53×** |

`pread()` 每次调用经历：用户态 → 内核态 → VFS 层 → 文件系统层 → 块设备层 → 用户态。
即使有 page cache，每次调用的固定开销约 0.3μs，16.3M 次累计 **~5000ms**。

`mmap` 将文件映射到虚拟地址空间后，读取变为普通内存访问（`memcpy`），由内核按需调页，无用户态/内核态切换。

### 根因 2: 对象创建开销 — 零分配 vs 每特征分配

```
GDAL component 每个特征的获取路径:
  GetNextFeature()
    → new OGRFeature            (堆分配 ~100ns)
    → 读取 blob 数据             (pread)
    → new OGRGeometry           (堆分配 ~100ns)
    → 设置几何对象到 Feature
    → 返回 Feature 给调用方
    → 调用方销毁 Feature         (堆释放 ~50ns)
  总计: ~250ns 对象开销/特征 × 8.17M = ~2000ms

explorgdb 每个特征的获取路径:
  peek_geometry_blob()
    → 数组查表 feature_offsets_[fid]   (O(1))
    → memcpy 到预分配 row_buffer_      (无分配)
    → 返回指针到内部 buffer
  总计: ~25ns/特征 × 8.17M = ~200ms
```

GDAL 的 `OGRFeature` + `OGRGeometry` 每次创建/销毁涉及多次堆操作。
explorgdb 使用单一 `row_buffer_`（只增不减），8M 次调用零次堆分配。

### 根因 3: 抽象层开销 — 直接解析 vs 虚函数分发

```
GDAL 调用栈（每个特征）:
  OGRLayer::GetNextFeature()        [虚函数]
    → OGRFileGDBLayer::_GetFeature()
      → FGDBLayer::GetFeature()
        → FileGDBAPI::Row::GetFeature()
          → 解码字段值...
  共 5~7 层虚函数/间接调用

explorgdb 调用栈:
  peek_geometry_blob()              [内联]
    → read_at() → memcpy            [内联]
    → BinaryReader 指针偏移          [内联]
  共 1~2 层，全部可内联
```

GDAL 的抽象层设计支持多格式驱动（FileGDB、Shapefile、GeoJSON...），但每个特征都要经过虚函数分发。
explorgdb 是 FileGDB 专用解析器，编译期确定所有调用，编译器可完全内联。

### 根因 4: 索引策略差异 — 空间索引 vs B+ 树

这是 **explorgdb 唯一落后** 的维度：

| 指标 | explorgdb | GDAL component |
|------|-----------|----------------|
| 索引类型 | .spx 网格索引 (线性扫描) | B+ 树 (对数查找) |
| Large_10M 查询耗时 | **656ms** | **0.2ms** |
| 差距 | 慢 3280× | — |

GDAL 的 B+ 树索引查询极快（0.2ms vs 656ms），但被 fetch 的 10922ms 完全淹没。

如果未来将 explorgdb 的空间索引从线性扫描改为 R-tree，索引查询可以从 656ms 降到 ~1ms，总耗时可从 1366ms 降到 ~700ms（再快 2×）。

## 3. 耗时分布对比

```
                    explorgdb (1,366ms)                    GDAL component (10,923ms)
                 ┌─────────────────────────┐            ┌─────────────────────────────────┐
  加载 (2%)      │ ██                      │            │                                 │
  索引查询 (48%) │ ████████████████        │            │                                 │
  peek (15%)     │ █████                   │            │                                 │
  bbox (14%)     │ ████                    │            │                                 │
  对象创建 (0%)  │                         │  fetch     │ ███████████████████████████████ │
  其他 (21%)     │ ███████                 │  (100%)    │                                 │
                 └─────────────────────────┘            └─────────────────────────────────┘
```

**关键洞察**: GDAL component 的 99.98% 时间花在 fetch 阶段，而 fetch 的瓶颈不是磁盘 I/O（page cache 命中），而是 **CPU 开销**：系统调用 + 堆分配 + 虚函数分发。

---

## 4. 结论

| 维度 | explorgdb 优势来源 | 贡献占比 |
|------|-------------------|---------|
| mmap 消除系统调用 | 16.3M 次 pread → 0 次 | ~50% |
| 零堆分配 | 8.17M 次 OGRFeature 创建 → 0 次 | ~30% |
| 内联 vs 虚函数 | 编译器优化 + 无间接调用 | ~15% |
| 索引策略劣势 | B+ 树 0.2ms vs 网格 656ms | -5% (被 fetch 淹没) |
| **合计** | — | **8.0×** |

简而言之: **GDAL 为每个特征付出了「创建对象 + 系统调用」的固定开销，而 explorgdb 将这两个开销都降到了零。** 当结果集从 1800 增长到 817 万时，固定开销的累积效应使差距从 1× 扩大到 8×。

## 5. 进一步优化空间

| 优化项 | 预期加速 | 难度 |
|--------|---------|------|
| R-tree 替代线性扫描 | 索引查询 656ms → ~1ms | 中 |
| SIMD 批量 bbox 过滤 | peek_bbox 185ms → ~30ms | 高 |
| 并行查询 (多线程) | 总耗时 / CPU 核数 | 中 |
| 预估总优化空间 | 1366ms → ~200ms | — |

即使完成全部优化，对比 GDAL component 的 fetch (10922ms)，explorgdb 的总耗时 (~200ms) 仍将快 **54×**。瓶颈已经从 I/O 转移到了算法层面（索引结构、过滤策略）。
