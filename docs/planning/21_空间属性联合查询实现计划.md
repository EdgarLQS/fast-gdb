# 21 — 空间与属性联合查询实现计划

- **更新日期**：2026-07-17
- **状态**：待执行
- **实现基线**：`main@5647c6a`
- **建议分支**：`codex/spatial-attribute-query`
- **当前操作**：仅编写计划，尚未创建分支或修改代码

## 1. 目标与成功标准

在 `QueryEngine` 中提供单次空间与属性联合查询入口，调用方只需提供 bbox 和当前 WHERE 子集，不再自行执行两次查询并求 FID 交集。

成功标准：

1. 联合查询结果等于“精确空间相交 FID 集 ∩ WHERE 命中 FID 集”。
2. Point、MultiPoint、Polyline、Polygon 及 Z/M/ZM 不改变既有精确空间语义。
3. 单个可索引属性比较能同时使用 `.spx` 和 `.atx`；复合 WHERE 或缺索引时在空间候选上评估属性，不默认全表执行两次。
4. 结果 FID 升序、唯一，并与 GDAL `SetSpatialFilterRect + SetAttributeFilter` 的完整 FID 集一致。
5. 既有 `SpatialBbox`、`AttributeDouble`、`AttributeString` 和 `WhereClause` 的公开行为、执行结果和安装面保持兼容。
6. 新增 100K 和现有 10M fixture 性能基准；先验证正确性，再比较联合查询耗时。

## 2. 当前实现与问题

`QueryRequest` 当前由互斥的 `QueryKind` 分派：

- `SpatialBbox` 调用 `query_bbox_unified()`，使用 `.spx` 候选或 geometry-only 扫描后做精确空间判断。
- `AttributeDouble` / `AttributeString` 调用 `.atx` 查询。
- `WhereClause` 解析当前支持的比较、`AND`、`OR`、`IN` 和括号，然后顺序扫描全表。

现有接口无法在一个请求中表达 bbox 和 WHERE；调用方手工求交集会复制排序、去重、错误处理和性能策略，也无法对两种候选的选择性统一规划。

## 3. 公开接口设计

### 3.1 最小新入口

在 `query_engine.h` 中增加：

```cpp
enum class QueryKind {
    ReadByFid,
    SequentialScan,
    SpatialBbox,
    AttributeDouble,
    AttributeString,
    WhereClause,
    SpatialWhere
};
```

`QueryRequest` 已有 bbox 和 `where_clause` 字段，`SpatialWhere` 直接复用它们，不再增加一组重复参数：

```cpp
QueryRequest request;
request.kind = QueryKind::SpatialWhere;
request.xmin = 0.0;
request.ymin = 0.0;
request.xmax = 10.0;
request.ymax = 10.0;
request.where_clause = "population >= 1000 AND category = 'A'";

QueryResult result = engine.query(request);
```

不增加 `query_spatial_attribute_double()` / `query_spatial_attribute_string()` 等组合方法。组合、候选规划和回退都应位于 `QueryEngine` 模块内，保持单一对外接口。

### 3.2 结果诊断

扩展 `QueryResult` 中的执行路径与统计，不暴露内部 parser 类型。新的 `execution_path` 固定为以下之一：

- `spatial-where:spx+atx`：空间与属性都由索引缩小候选。
- `spatial-where:spatial-candidates`：先得到精确空间命中，再仅对这些 FID 评估 WHERE。
- `spatial-where:sequential`：空间索引不可用且规划器选择单次顺序扫描。
- `spatial-where:invalid`：bbox 或 WHERE 非法，不执行查询。

在 `SpatialQueryMetrics` 之外增加联合查询指标，建议新建 `CombinedQueryMetrics` 并作为 `QueryResult` 成员：

```cpp
struct CombinedQueryMetrics {
    size_t spatial_candidate_count = 0;
    size_t spatial_match_count = 0;
    size_t attribute_candidate_count = 0;
    size_t attribute_tested = 0;
    size_t final_match_count = 0;
    double spatial_ms = 0.0;
    double attribute_ms = 0.0;
    double intersection_ms = 0.0;
    double total_ms = 0.0;
    bool used_spatial_index = false;
    bool used_attribute_index = false;
};
```

字段只用于诊断和性能证据，不改变匹配语义。

## 4. 实现方案

### 4.1 WHERE 编译与可索引判定

将当前位于 `query_engine.cpp` 的 WHERE tokenizer、parser、字段验证和求值逻辑整理为 Reader 内部模块，例如 `query_where_internal.h/.cpp`。该模块的内部接口只需要：

```cpp
CompiledWhere compile_where(
    const std::string& text,
    const std::vector<FieldDescriptor>& fields);

bool evaluate_where(
    const CompiledWhere& expression,
    const FieldRef* fields,
    int field_count);
```

`CompiledWhere` 内部保留语法树和字段位置，并提供“是否为单个可 `.atx` 化比较”的判定。首版快速路径仅包括：

- 单个数值或字符串字段；
- `=`、`!=`、`<`、`<=`、`>`、`>=`；
- Catalog 中能找到该字段对应的 `.atx`。

`AND`、`OR`、`IN` 和括号仍正确支持，但首版不将复合表达式拆成多个 `.atx` 计划，而是在空间候选上求值。这保持正确性，同时限制首版规划器复杂度。

### 4.2 联合执行策略

`QueryEngine::query_spatial_where()` 按以下顺序执行：

1. 验证 bbox 全部为有限数、`xmin <= xmax`、`ymin <= ymax`。
2. 编译 WHERE；空字符串、语法错误或未知字段立即返回可诊断失败，不将失败当作零命中。
3. 通过既有 `query_bbox_unified()` 得到经精确空间判断后的升序 FID。
4. 若 WHERE 是单个可索引比较，通过 `.atx` 得到升序 FID，使用线性双指针交集，不使用 `unordered_set`。
5. 若 WHERE 不可索引，只读取空间命中 FID 对应的属性并求值，不再扫描全表。
6. 恢复最终 FID 升序，写入 `CombinedQueryMetrics`，保留 `SpatialQueryMetrics.invalid_geometries` 等原始空间诊断。

为避免对每个 FID 构造完整 `FeatureRecord`，在 `GdbTableParser` 内增加候选字段扫描实现，语义对齐现有 `scan_geometry_candidates()`：

```cpp
uint64_t scan_field_candidates(
    const std::vector<uint32_t>& candidates,
    ScanCallback callback);
```

该实现在内部按物理偏移排序、读取并复用 `FieldRef` 解析，但对外返回的最终 FID 仍按数值升序。不新建另一套属性值类型或 WHERE 求值器。

### 4.3 索引缺失与回退

- `.spx` 缺失或解析失败：复用现有 geometry-only 顺序扫描和精确空间判断。
- `.atx` 缺失：在空间命中 FID 上评估 WHERE，`execution_path` 标记为 `spatial-where:spatial-candidates`。
- 空间候选为空：立即返回成功的空结果，不打开 `.atx` 或扫描属性。
- 属性候选为空：返回成功的空结果，不再读取字段。
- 非法几何：保留现有 fail-closed 和 `invalid_geometries` 语义，不因属性条件将其隐藏成普通不匹配。
- WHERE 编译失败：`execution_path=spatial-where:invalid`，`fallback_reason` 保留具体原因。

### 4.4 不在首版范围

- 多个 `.atx` 的代价优化和布尔索引计划。
- 通用 SQL、JOIN、聚合、ORDER BY、LIMIT 或重投影。
- 任意几何谓词；首版仅组合当前 bbox intersects 语义与 WHERE 子集。
- 联合查询结果物化缓存。
- 并行候选评估。先建立单线程正确性和可重复性能基线。

## 5. 测试计划

### 5.1 单元测试

为 WHERE 内部模块和 FID 交集增加纯单元测试：

- 空、单个、完全不相交、完全包含、重复输入的升序 FID 交集。
- 数值与字符串六种比较操作。
- `AND`、`OR`、`IN`、括号和大小写字段名。
- 空值、未知字段、语法错误、非法数字和空 WHERE。
- 仅单比较被识别为首版 `.atx` 快速路径，复合表达式不被错误拆分。

### 5.2 QueryEngine 集成测试

现场生成带 `.spx` 和 `.atx` 的 Point 与 Polygon FileGDB，覆盖：

1. bbox 命中多行，属性再缩小到单行。
2. 属性命中多行，空间条件再缩小。
3. 空间空集、属性空集和最终交集为空。
4. 边界接触、线穿越 bbox、Polygon 含洞等精确空间判断。
5. 字符串、整数、浮点、负数、NULL 和非 ASCII 字符串。
6. 有 `.spx + .atx`、只有 `.spx`、只有 `.atx` 和两种索引都不可用。
7. 非法 bbox、错误 WHERE、未知字段和损坏索引的可诊断行为。
8. 结果 FID 严格升序、无重复，且等于分别执行后的集合交集。
9. 既有各 `QueryKind` 的回归结果和 `execution_path` 不变。

### 5.3 GDAL 等价性测试

对同一数据集使用 GDAL：

```cpp
layer->SetSpatialFilterRect(xmin, ymin, xmax, ymax);
layer->SetAttributeFilter(where_clause.c_str());
```

逐条收集 GDAL FID，按项目已冻结的 ObjectID/FID offset 转换后，与 fast-gdb 完整 FID 向量对比。不只比较 count 或 hash。

### 5.4 构建与回归

- GDAL ON Release：构建完整目标并运行完整 CTest。
- GDAL OFF Release：联合查询仍可编译和运行；GDAL 只用于测试对照，不泄露到 Reader 公开头。
- 独立 package consumer：安装后使用 `fast_gdb::linear` 编译并运行 `SpatialWhere` 示例。
- 回归检查：`git diff --check main...HEAD`，没有构建目录、fixture 或 benchmark 原始输出误提交。

## 6. 性能基准与门禁

### 6.1 数据与场景

新增 schema-v2 联合查询 manifest，不在日常测试中重新生成 10M fixture。

100K 现场数据覆盖：

- 空间 1% + 属性高选择性（最终约 0.1%）。
- 空间 10% + 属性中选择性（最终约 5%）。
- 空间 80% + 属性高选择性。
- 空间 100% + 属性低选择性。
- 复合 WHERE，强制走 `spatial-candidates` 路径。

10M 复用 Point、MultiPoint、Polyline fixture，首版选择 1%、10%、30%、80% 四档 bbox，每档组合高、中、低三种属性选择性。若现有 fixture 没有可用 `.atx` 字段，先使用 100K 数据完成 `.spx + .atx` 门禁，10M 只测候选 WHERE 路径；不为满足基准而拷贝或重建三份 10M fixture。

### 6.2 对照组

每个场景至少记录：

1. fast-gdb 联合查询。
2. fast-gdb 旧方式：分别空间/属性查询后由 benchmark 求交集。
3. GDAL `SetSpatialFilterRect + SetAttributeFilter`。
4. 固定 `main@5647c6a` baseline；该 baseline 不支持联合入口，因此使用第 2 种旧方式作为 main 对照。

采用 Release/profile-off、current/main 交替、5 次采样，输出 median、p95、候选数、最终结果数、完整 FID 验证、分段耗时和执行路径。

### 6.3 性能判定

- 正确性、FID 一致、`invalid_geometries=0` 和执行路径一致是性能数字有效的前置。
- `.spx + .atx` 快速路径相对 current 的调用方求交集基线不得回退超过 5%。
- `spatial-candidates` 复合 WHERE 路径相对“空间查询 + 全表 WHERE + 调用方交集”应有稳定改善；首版完成判据为中位耗时至少改善 5%。
- 任一现有纯空间、纯属性或 WHERE 性能回归超过 5% 时不能接受。
- 不将“快于 GDAL”设为所有选择性的绝对门禁；必须报告 fast/GDAL 比值并解释不同执行路径。

## 7. 实施顺序与提交拆分

按以下顺序实施，每个提交都必须可编译并通过当时相关测试：

1. **内部 WHERE 模块化**：移动解析和求值逻辑，不改变现有 `WhereClause` 行为；先用现有和新增单元测试锁定兼容性。
2. **候选字段扫描**：增加 `scan_field_candidates()` 和物理顺序读取测试，不接入新查询类型。
3. **联合查询正确性**：增加 `SpatialWhere`、空间候选 + WHERE 求值和完整集成测试。
4. **`.spx + .atx` 快速路径**：增加单比较索引判定、双指针交集和执行诊断。
5. **GDAL 等价性与 package consumer**：补齐 GDAL FID 对照、GDAL OFF 和安装消费测试。
6. **性能 runner 与基线**：增加 schema-v2 结果、100K/10M 矩阵和 5% 回退门禁。
7. **文档收口**：更新组件使用、功能覆盖矩阵、性能证据和项目综合汇报，将联合查询从“尚未实现”改为实际验收状态。

## 8. 审核与验收判定

### 8.1 必查项

- 公开头没有泄露 GDAL、WHERE AST、parser 或 benchmark 类型。
- 旧 `QueryKind` 枚举值的源码兼容性保留；`SpatialWhere` 只追加在枚举末尾。
- 公开请求只新增一种组合类型，不为数值/字符串组合复制方法。
- 候选物理顺序与最终 FID 数值顺序没有混淆。
- `.atx` 或 `.spx` 缺失不会把合法查询静默变成空结果。
- 非法请求与合法零命中具有不同诊断。
- 联合查询没有放宽精确几何判断或隐藏 `invalid_geometries`。

### 8.2 判定

- **不可提交**：Release 构建不可确认，完整 FID 与 GDAL 不一致，旧查询语义回归，非法几何被静默接受，或发生公开安装面泄露。
- **修复后可提交**：正确性通过，但 package consumer、诊断路径、文档、性能矩阵或 5% 回退门禁未完成。
- **可提交**：GDAL ON/OFF Release、完整 CTest、联合查询集成测试、GDAL 完整 FID 对照、package consumer、100K/10M 性能矩阵和回归门禁全部通过。

## 9. 新分支启动检查清单

1. 确认当前工作区干净，并记录 `main` 实际 SHA。
2. 如 `main` 已不是 `5647c6a`，先审核 `5647c6a...main` 是否改变 QueryEngine、WHERE、索引或测试接口，再更新基线。
3. 从已验证的 `main` 创建 `codex/spatial-attribute-query`。
4. 实施前先运行 QueryEngine、空间查询和属性索引现有测试，保存基线结果。
5. 按第 7 节小步提交，不同时开展与联合查询无关的 Reader 重构。
