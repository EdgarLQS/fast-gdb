## 1. 目标与成功标准

在 `QueryEngine` 中提供单次空间与属性联合查询入口，并新增完整 Feature
流式迭代能力。调用方只提供查询条件，通过 `FeatureCursor::next()` 逐个取得
FID、全部字段和规范化 ISO WKB，不再自行求 FID 交集或按 FID 二次拼装对象。

成功标准：

1. 最终结果等于“精确空间相交 FID 集 ∩ 完整 WHERE 命中 FID 集”；
2. Point、MultiPoint、Polyline、Polygon 以及 Z/M/ZM 保持既有精确空间语义；
3. 单个可证明安全的比较同时利用 `.spx` 和 `.atx`；
4. 复合 WHERE、缺索引、损坏索引或不安全索引编码只在精确空间命中行上求值；
5. `.atx` 仅产生候选，最终必须执行完整 WHERE 复核；
6. 最终 FID 零基、升序、唯一，并与 GDAL 联合过滤完整 FID 向量一致；
7. 既有 `SpatialBbox`、属性查询和 `WhereClause` 语义保持兼容；
8. 内部 parser 不进入安装面；
9. `query()` 继续返回 FID 集，既有调用方无需迁移；
10. 游标不一次性保存全部完整 Feature，内存随单个 Feature 大小增长；
11. 正常 EOF 与读取/解码失败可明确区分，错误不得伪装成 EOF；
12. 实际构建、CTest、consumer 和性能证据齐全后才能 Accepted。

## 2. GDAL OpenFileGDB 参考实现

GDAL OpenFileGDB 的联合查询核心流程：

1. 空间过滤构建空间索引迭代器；
2. 属性表达式尝试构建属性索引迭代器；
3. 两种迭代器同时可用时执行有序 FID 交集；
4. 候选仍经过精确几何判断；
5. 属性索引不足以证明完整表达式时仍执行属性表达式复核。

参考源码入口：

- `ogr/ogrsf_frmts/openfilegdb/ogropenfilegdblayer.cpp`
  - `SetAttributeFilter()`
  - `BuildIteratorFromExprNode()`
  - `BuildCombinedIterator()`
  - `GetNextFeature()`
- `ogr/ogrsf_frmts/openfilegdb/filegdbindex.cpp`
  - `FileGDBIterator::BuildAnd()`
  - `FileGDBIterator::BuildOr()`

fast-gdb 首版采用更保守的候选规则：

- 所有 `.atx` 路径都执行完整 WHERE 复核；
- 字符串只对当前可证明安全的 `=` 和 `>=` 使用候选；
- 非 BMP 字符串回退，避免 surrogate pair 解码造成假阴性；
- `!=` 回退，避免 NaN 比较造成候选不完备；
- Int16、Float32、Int64 等不能由当前 trailer 唯一确定物理语义的编码不进入快速路径；
- `LOWER(field)` 和其他函数索引只用于字段关联，不用于直接比较快速路径；
- 复合 `AND`、`OR`、`IN` 首版不构造布尔索引计划。

## 3. 公开接口

`QueryResult` 增加 `CombinedQueryMetrics`，记录空间候选、精确空间命中、属性候选、WHERE 复核数、最终命中、阶段耗时和索引使用情况。指标只用于诊断，不改变查询语义。

### 3.1 完整 Feature 流式接口

在 `query_engine.h` 的公开安装面新增：

```cpp
struct QueryFeature {
    uint32_t fid = 0;
    FeatureRecord record;
    GeometryValue geometry;
};

class FeatureCursor {
public:
    FeatureCursor(FeatureCursor&&) noexcept;
    FeatureCursor& operator=(FeatureCursor&&) noexcept;
    FeatureCursor(const FeatureCursor&) = delete;
    FeatureCursor& operator=(const FeatureCursor&) = delete;
    ~FeatureCursor();

    bool next(QueryFeature& feature);
    bool done() const noexcept;
    const QueryResult& query_result() const noexcept;
    const std::string& error() const noexcept;

private:
    class Impl;
    explicit FeatureCursor(std::unique_ptr<Impl> impl);
    std::unique_ptr<Impl> impl_;
    friend class QueryEngine;
};

class QueryEngine {
public:
    FeatureCursor open_cursor(const QueryRequest& request);
};
```

`FeatureCursor` 是深模块：公开接口只暴露打开、取下一条、结束状态、查询诊断和
错误；FID 规划、物理读取顺序、字段解析、几何解码和缓存均留在 `Impl` 中。
`Impl` 定义在 `.cpp`，不得把 `GdbTableParser`、`FieldRef` 或内部 WHERE 类型放入
安装面。

实现落点固定为：声明放在 `query_engine.h`；游标 PImpl 和状态机放在新增的
`feature_cursor.cpp`；`QueryEngine::open_cursor()` 与活动游标守卫的薄适配留在
`query_engine.cpp`；构建清单显式加入新源文件。GDAL OFF 测试新增
`test_feature_cursor.cpp`，GDAL 对等测试新增 `test_feature_cursor_gdal.cpp`，不要把
游标实现塞入已较长的联合查询源文件。

### 3.2 `QueryFeature` 完整对象语义

- `fid` 使用 fast-gdb 既有零基 FID；与 GDAL 比较时仍按现有规则转换 GDAL FID；
- `record.fid == fid`，`record.field_values` 与 `QueryEngine::table()->fields()` 顺序一致；
- `record` 必须保持 `read_by_fid()` 的既有兼容语义，包括 NULL、Binary 原始字节、
  DateTimeWithOffset，以及 Geometry 槽位中的兼容 WKT；
- “全部字段”限定为当前 Reader 支持的记录语义；Raster 字段仍按既有行为返回 NULL
  占位，不在本任务中增加像素解码；
- `geometry` 是同一行几何的规范化 `GeometryValue`，主要输出为 ISO WKB，并保留
  SRID、Z/M、曲线线性化、backend、status 和 diagnostic；
- 无几何字段的表返回有效属性 Feature：`geometry.status` 设为
  `UnsupportedType`，diagnostic 为 `table has no geometry field`，不因此终止游标；
- 空几何返回 `GeometryStatus::Empty`，属于成功对象；损坏几何、明确不支持且无法
  安全线性化的几何属于单条 Feature 解码失败，游标进入错误状态；
- `next()` 成功时必须完整覆盖输出参数，失败时不得留下“半更新”对象。实现使用
  局部 `QueryFeature candidate`，全部读取成功后再 move 到调用方对象。

首版允许复用 `read_record_by_fid(fid, record)` 与
`read_geometry_value(fid, geometry)` 两条成熟路径，以正确性优先。由于这会对同一
FID 定位两次并可能分别生成 WKT/WKB，必须在 profile 中单列；只有证据显示它是
热点后，才新增 parser 内部“一次定位、一次几何模型解码、同时生成兼容 WKT 与
ISO WKB”的深层读取函数。该优化不得改变公开结构或旧 `read_by_fid()` 语义。

### 3.3 状态机、生命周期和错误语义

游标只有四个内部状态：`Ready`、`Exhausted`、`Failed`、`MovedFrom`。

| 当前状态 | 操作 | 结果 |
|---|---|---|
| Ready | `next()` 读到对象 | 返回 `true`，仍为 Ready |
| Ready | 候选耗尽 | 返回 `false`，转为 Exhausted |
| Ready | 行读取或几何解码失败 | 返回 `false`，转为 Failed |
| Exhausted | 再次 `next()` | 恒定返回 `false` |
| Failed | 再次 `next()` | 恒定返回 `false`，保留首次错误 |
| MovedFrom | 任意查询 | `next()` 返回 `false`，`done()` 为 true |

状态判定固定如下：

- 正常结束：`next() == false && done() == true && error().empty()`；
- 失败结束：`next() == false && done() == false && !error().empty()`；
- `query_result()` 在打开时即保存查询执行路径、fallback 和指标，生命周期覆盖整个
  游标；其 `matched_fids` 对候选模式保存最终 FID 集，对真正顺序流模式保持为空，
  避免为了诊断重新物化全量 FID；
- 游标可移动、不可复制；移动后读取状态和缓冲区只属于新对象；
- `QueryEngine`、`GdbCatalog` 和 `ResolvedTable` 必须比游标活得更久；首版不复制
  parser 或文件句柄；
- 同一个 `QueryEngine` 同时只允许一个活动游标。第二次 `open_cursor()` 返回 Failed
  游标，错误固定为 `another feature cursor is active`；旧游标析构、正常耗尽或失败后
  释放占用；
- `open_cursor()` 必须先完成请求校验和候选规划，再登记活动游标，避免内部调用
  `query()` 被自己的守卫拒绝；安全 fallback 不是错误，只有 engine 未打开、请求非法
  或既有查询明确返回 `*:invalid` 执行路径才生成 Failed 游标；
- `QueryEngine::open()`、`query()`、`read_by_fid()` 和 `scan()` 在活动游标期间不允许
  调用，分别返回 `false`、带 `feature cursor is active` fallback 的空结果、`false`
  和 `0`；不引入隐式锁，也不承诺线程安全；
- 首次失败锁定，后续操作不得覆盖原始错误。

活动所有权随 move 转移。move 赋值前，目标若持有另一个活动游标，必须先按析构同样
的路径释放其 engine；源对象随后进入 MovedFrom。所有释放路径调用同一个幂等内部
函数，并携带 engine 分配的单调 `cursor_generation`；engine 只接受当前 generation
的释放，防止已耗尽旧游标的迟到析构误清除新游标占用。活动期间不得移动或销毁
`QueryEngine`。调用方提前停止迭代时，应让游标离开作用域；首版不新增 `close()`。

### 3.4 两种执行模式

`open_cursor()` 先校验 engine 已打开和请求合法，再根据请求选择模式：

1. **候选 FID 模式**：适用于 `ReadByFid`、`SpatialBbox`、属性索引、
   `WhereClause` 和 `SpatialWhere`。首版调用既有 `query(request)` 生成语义已经确认的
   升序唯一 FID，然后按序逐 FID 完整读取；只物化 `vector<uint32_t>`，不物化完整
   Feature；
2. **顺序流模式**：适用于 `SequentialScan`。不得先调用
   `query_sequential_scan()` 生成全表 FID；游标维护下一个待查 FID，并依据 tablx
   存在位跳过删除槽，逐条读取完整对象。后续 WHERE 无索引路径是否改为边扫描边
   过滤，必须由 profile 驱动，不放入首版。

所有模式对外保持 FID 升序、唯一。`ReadByFid` 最多产生一个对象；空命中是正常
EOF。查询条件非法、engine 未打开或内部查询返回语义错误时，`open_cursor()` 直接
返回 Failed 游标，不允许降级为零结果。

### 3.5 调用示例

```cpp
explorgdb::QueryRequest request;
request.kind = explorgdb::QueryKind::SpatialWhere;
request.xmin = 0.0;
request.ymin = 0.0;
request.xmax = 10.0;
request.ymax = 10.0;
request.where_clause = "population >= 1000";

auto cursor = engine.open_cursor(request);
explorgdb::QueryFeature feature;
while (cursor.next(feature)) {
    consume(feature.fid,
            feature.record.field_values,
            feature.geometry.wkb);
}
if (!cursor.done()) {
    std::cerr << cursor.error() << '\n';
}
```

调用方必须在循环后检查 `done()`；只写 `while (next())` 会把读取失败误当结束，
package consumer 和使用文档都必须展示完整检查方式。

### 4.4 联合执行

`QueryEngine::query_spatial_where()`：

1. 校验 bbox；
2. 编译并绑定 WHERE；
3. 调用 `query_bbox_unified()` 得到精确空间命中；
4. 空间空集直接返回；
5. 单个安全比较解析 `.gdbindexes` 与 `.atx`；
6. `.atx` 候选排序、去重；
7. 与精确空间 FID 线性交集；
8. 对交集候选执行完整 WHERE 复核；
9. 缺失、损坏或不安全 `.atx` 回退到精确空间命中行求值；
10. 最终 FID 排序、去重并写入联合指标。

### 4.5 `.atx` fail-closed

三轮自审后增加：

- 文件长度、`streamoff`、`size_t`、`streamsize` 边界；
- 页面区必须为 4096 字节整数倍；
- tree depth、页号、页容量和 FID 校验；
- 叶页链访问预算，阻止循环页链；
- 页偏移 64 位中间计算；
- 实际条目数必须等于 trailer `total_value_count`；
- 任一结构错误都返回解析失败并清空条目。

合法零命中允许空候选；文件缺失或结构损坏禁止使用索引快速路径。

- 对照联合入口、旧式双查询求交和 GDAL；
- 每轮逐 FID 校验；

### 6.1 完整对象端到端基准

现有空间 benchmark 只对齐最终 FID 集：fast-gdb 返回候选 FID，而 GDAL
`GetNextFeature()` 已构造完整 `OGRFeature`。它可以说明 FID 过滤效率，不能证明完整
对象读取速度。新增 runner 必须把两类结果分开报告：

1. **FID-only**：保留现有语义，用于观察索引、候选和精确空间判断；
2. **Full-feature stream**：fast-gdb 使用 `FeatureCursor::next()`；GDAL 使用
   `GetNextFeature()`。双方都读取全部字段、导出 ISO WKB，并把
   `FID + 字段类型/NULL/值 + WKB` 写入相同的无分配 checksum sink。

Full-feature 计时范围固定为：打开数据源/engine、设置或编译过滤条件、取得全部完整
对象、WKB 生成和 checksum sink；不包含 fixture 生成、日志写盘和结果 JSON 序列化。
不得把完整对象保存到 vector，避免 10M 数据导致内存失真。

每个场景记录：

- `result_count`、完整 FID checksum、字段 checksum、WKB checksum、输出字节数；
- `open_ms`、`plan_ms`、`iterate_ms`、`total_ms`、median、p95、features/s；
- peak RSS；fast-gdb 的 execution path、空间/联合指标和游标执行模式；
- `correctness`，只有 count、FID、字段、WKB 和输出字节全部一致才为 PASS。

数据矩阵：

- 100K Point：空间覆盖率 1%、30%、100%，分别运行 SpatialBbox 与 SpatialWhere；
- 10M Point、MultiPoint、Polyline：先运行 1%、30%、100%，空间允许后再补 10%、80%；
- fresh-open，fast-gdb/GDAL 交替，预热轮不计，正式 5 次，报告 median 和 p95；
- 明确标记 fresh-open，不宣称 strict-cold；正确性失败时耗时结果无效。

性能判定分开执行：FID-only 相对当前基线不得回退超过 5%；Full-feature cursor 相对
“同一版本 `query()` + 逐 FID `read_by_fid()` + `read_geometry_value()`”不得回退超过
5%。与 GDAL 的结果如实报告，首版不要求一定快于 GDAL。profile 至少拆分查询规划、
FID/行定位、字段物化、兼容 WKT、GeometryModel、WKB、sink；若双定位或双几何解码
是主要热点，再实施 3.2 的单行联合解析优化并重新跑完整正确性矩阵。
