## P0：写入器系统表更新

**来源**：第三章 3.5 节 + `docs/technical/03_技术探索与教训.md` 第 4 节

**问题**：explorgdb 的直接写入可通过自身验证，但 GDAL 无法读取写入结果。原因是 `a00000000.gdbtable` 系统表未被更新，GDAL 依赖该表获取数据集元数据。

- 实现 `update_system_tables()` 函数，写入器在完成数据写入后更新系统表
- 验证：写入后使用 GDAL 的 OpenFileGDB 驱动读取，确认数据一致
- 补充测试：写入后双方读取对比

**工作量评估**：~4-5 天

## P1：补充 Surrogate Pair 支持

**来源**：第三章 3.5 节

**问题**：当前 `utf16le_to_utf8()` 和 `utf8_to_utf16()` 不支持 UTF-16 代理对（U+D800~U+DFFF），导致：
- 4 字节 UTF-8 字符（emoji 😀、生僻字 𠀀）无法正确转换
- `string_index_key_supported()` 返回 false → .atx 索引查询回退到全表扫描

**范围**：
- `src/edgar/explorgdb/common/utf16.cpp` — 修改 `utf16le_to_utf8()` 检测并处理 surrogate pair：遇到高代理位（U+D800~U+DBFF）时读取下一个低代理位（U+DC00~U+DFFF），组合为完整码点，输出 4 字节 UTF-8 序列
- `src/edgar/explorgdb/common/utf16.cpp` — 修改 `utf8_to_utf16()` 支持 4 字节 UTF-8 序列 → 代理对
- `src/edgar/explorgdb/reader/query_engine_combined.cpp` — 更新 `string_index_key_supported()` 逻辑，在编码器支持 surrogate pair 后允许非 BMP 字符使用索引
- `tests/edgar/explorgdb/common/test_utf16.cpp` — 补充测试用例：emoji（😀 U+1F600）、生僻字（𠀀 U+20000）、边界值（U+FFFF、U+10FFFF）

**工作量评估**：~2-3 天

## P3：GBK/GB2312 编码输入文档化

**来源**：第三章 3.5 节

**问题**：当前代码库只接受 UTF-8 输入，但未明确文档化。如果用户传入 GBK 编码的路径或字符串：
- 路径：`fast_gdb_open_utf8()` 的 `MultiByteToWideChar(CP_UTF8)` 会失败，然后回退到 `CP_ACP`（系统 ANSI 代码页）
- 写入器：`count_utf8_codepoints()` 会拒绝非法 UTF-8 序列
- 行为不可预测，用户可能遇到"乱码"或"写入失败"

**范围**：
- 在 API 文档（`docs/usage/`）中明确声明 UTF-8 输入要求
- 在 API 层添加编码检测（可选）：检测输入是否为有效 UTF-8，拒绝非 UTF-8 输入并给出明确错误信息
- 补充测试：传入 GBK 编码字符串，验证错误处理行为

**工作量评估**：~1-2 天
