# S3.4 64-bit ObjectID safety boundary

## Finding

- GDAL's [OpenFileGDB source](https://github.com/OSGeo/gdal/blob/master/ogr/ogrsf_frmts/openfilegdb/filegdbtable.h#L2567-L2582) defines table version 3 as a 32-bit ObjectID format and version 4 as a 64-bit ObjectID format. Its [v4 table reader](https://github.com/OSGeo/gdal/blob/master/ogr/ogrsf_frmts/openfilegdb/filegdbtable.cpp#L793-L919) reads the record count at byte offset 16 and field-section offset at byte offset 32; the [v4 tablx reader](https://github.com/OSGeo/gdal/blob/master/ogr/ogrsf_frmts/openfilegdb/filegdbtable.cpp#L682-L762) uses a different fixed header from the prior local assumption. GDAL also tracks that some sparse v4 tables may not have reliable ObjectID mappings. The [driver documentation](https://gdal.org/en/stable/drivers/vector/openfilegdb.html#limitations) says sparse 64-bit OBJECTID support is read-only and incomplete and can emit non-faithful IDs.
- A local scan found 301 `.gdbtable` files and 304 `.gdbtablx` files under `test_data`; all had version 3. The incomplete `testcurve.gdb` remains unsuitable as a version-4 acceptance sample.
- Before this correction, the native `.gdbtablx` parser accepted version 4 but did not decode its offset map. The version-4 feature-block count stayed at the default zero, so a syntactically valid table could be reported as successfully parsed with no rows. The `.gdbtable` parser also read the v4 record count and field-section offset four bytes later than GDAL's upstream reader, and it could pair that table with a version-3 row-slot index.

## Initial fail-closed change

- At the time of this change, `GdbTableParser::open()` and `parse_header()` rejected version-4 table headers before exposing header or schema values, and `load_tablx()` only permitted version 3.
- At the time of this change, `GdbTablxParser` rejected version-4 indexes instead of returning a successful empty index.
- Regression coverage expected synthetic version-4 table and index inputs to fail closed. These checks were replaced by dense-v4 parsing coverage when the synthetic GDAL reference fixture was added.
- The format tutorial recorded GDAL's upstream v4 header offsets.

## Status after dense v4 baseline

The fail-closed behavior for unknown bitmap layouts remains. A later change added
support for v4 headers and dense, no-bitmap records, with an explicit synthetic
GDAL-reader fixture. It does not implement sparse/high ObjectID mapping or
complete SPX/ATX/query/API propagation. The current details and verification are
in [the dense v4 baseline record](2026-11-06-S3.4-dense-v4-baseline.md).
