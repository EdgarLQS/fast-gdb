# VersionedGdbStore 当前实现风险、陷阱与误用清单

- **审查标签**：@深度研究
- **日期**：2026-07-22
- **用途**：代码审查、生产接入、故障复盘和后续设计输入
- **原则**：风险按“触发条件 → 被破坏的不变量 → 现象 → 后果 → 当前保护 → 建议”描述

## 1. 风险等级定义

| 等级 | 定义 |
|---|---|
| P0 | 可能破坏 CURRENT、已发布 generation 或恢复链，造成数据不可用、丢失或错误删除 |
| P1 | 不一定破坏数据，但会导致服务不可用、容量失控、死锁式阻塞、长期错误读取或错误运维 |
| P2 | 主要造成性能突变、行为差异、兼容性误判或难以诊断 |
| P3 | 可维护性、可观测性或测试完整性问题，短期内不直接破坏正确性 |

## 2. 协议绕过风险

### 2.1 直接打开 published generation 进行写入

- **等级**：P0
- **触发**：ArcGIS、GDAL、QGIS 或自定义工具以 update 模式打开 `generations/gen-*.gdb`。
- **破坏不变量**：已发布 generation 不可变。
- **典型现象**：旧 Reader 在同一路径读取到变化；validator 通过的版本后来被修改；恢复后内容与发布证据不一致。
- **后果**：Reader snapshot 不再是快照；任何 GC、回滚、审计都失去可信基础。
- **当前保护**：代码只约束自身 Writer，不阻止外部进程。
- **建议**：
  - 文档定义为明确不支持；
  - publish 后尽可能收紧 generation 文件权限；
  - 增加 generation fingerprint/metadata；
  - `open()` 时抽查不可变标记或 hash；
  - 未来引入跨进程 store owner lock。

### 2.2 只保存 snapshot.path()，提前销毁 snapshot

- **等级**：P0/P1
- **触发**：调用方把 path 交给长期任务、GDAL Dataset 或缓存，然后释放 snapshot。
- **破坏不变量**：租约覆盖全部派生资源。
- **典型现象**：旧 generation 被 GC 后，外部对象仍访问已删除路径；Linux 上已打开 fd 可能继续工作，Windows 上删除可能失败，跨平台表现不一致。
- **后果**：间歇性读取失败、路径消失、磁盘清理异常、平台差异。
- **当前保护**：API 返回 snapshot，但无法阻止调用方仅保存字符串。
- **建议**：
  - 文档禁止裸 path 跨生命周期传播；
  - 为 Reader context 提供持有 snapshot 的封装；
  - debug 模式跟踪最老租约和派生对象；
  - 代码示例中 snapshot 必须处于最外层作用域。

### 2.3 外部系统长期绑定某个 generation 路径

- **等级**：P1
- **触发**：把 `gen-123.gdb` 注册到 ArcGIS Server、定时任务、配置文件或数据源连接。
- **破坏不变量**：generation 由 Store 租约管理，可在无租约时回收。
- **后果**：外部系统路径突然失效，或者为了避免失效被迫永久关闭 GC。
- **建议**：对外暴露托管读取服务，不暴露 generation 目录；若必须外部绑定，应使用独立导出副本，不属于 Store。

### 2.4 手工修改 CURRENT

- **等级**：P0
- **触发**：运维直接编辑文本、软链接替换、脚本 echo、文件浏览器复制覆盖。
- **破坏不变量**：CURRENT 是通过协议持久化的唯一事实来源。
- **后果**：路径穿越、目标缺失、未刷盘、指向 work、指向未验证 generation、恢复推理错误。
- **当前保护**：严格单行解析、路径校验和目标存在性检查。
- **建议**：所有切换必须走 Store 或受控 doctor/rollback 工具；手工编辑只允许在停机 runbook 中作为最后手段。

## 3. 多进程与并发风险

### 3.1 两个进程同时 Writer

- **等级**：P0
- **触发**：两个服务实例、滚动升级重叠、定时任务和主服务同时打开同一 store。
- **破坏不变量**：同一 store 只有一个 Writer。
- **可能序列**：
  1. A、B 同时读取 CURRENT=gen-10；
  2. A 创建 work-11，B 创建 work-12；
  3. A 发布 gen-11；
  4. B 仍基于 gen-10 发布 gen-12；
  5. A 的修改被 B 覆盖，产生 lost update；
  6. 任一进程可能回收另一进程仍在使用的 generation。
- **当前保护**：只有进程内 registry。
- **建议**：在跨进程锁实现前，部署层必须保证单实例 Writer；启动时用 sidecar owner file + OS lock fail-fast。

### 3.2 跨进程 Reader 未登记

- **等级**：P0/P1
- **触发**：另一个进程直接读取 CURRENT generation，但不持有 Store 租约。
- **破坏不变量**：GC 只依据进程内租约。
- **后果**：本进程可能删除外部 Reader 正在使用的旧 generation；Windows 和 POSIX 行为不同。
- **建议**：跨进程 Reader 明确不支持；未来需持久租约目录、心跳、PID/start-time 防重用和 stale lease 回收协议。

### 3.3 一个进程 refresh，派生对象仍活着

- **等级**：P1
- **触发**：QueryEngine、cursor、GDAL Dataset、异步回调或 mmap 未关闭即 refresh。
- **破坏不变量**：snapshot 绑定 generation，派生对象不能跨重绑定。
- **后果**：对象内部路径、索引和内存映射指向旧版，外层 snapshot 已转到新版，产生混合代次状态。
- **建议**：refresh 仅允许 idle 状态；增加活动派生对象计数或把 refresh 设计为返回新 snapshot，而不是修改原对象。

### 3.4 同一 QueryEngine/cursor 跨线程复用

- **等级**：P1/P2
- **触发**：线程池共享一个 cursor 或 Dataset。
- **后果**：迭代状态、缓存和错误状态竞争；即便底层文件只读也不代表对象线程安全。
- **建议**：每线程独立 Reader/QueryEngine/cursor；共享的只有不可变 generation 和显式只读元数据。

## 4. GDAL/ArcGIS 生命周期风险

### 4.1 publish 前 GDAL Dataset 未关闭

- **等级**：P1
- **触发**：仅调用 FlushCache，不销毁 Dataset；Layer、Feature、SQL result set、transaction 仍存活。
- **风险**：
  - 延迟写未完成；
  - `.lock` 或文件句柄仍存在；
  - Schema/extent/index 缓存未写回；
  - Windows promote/rename/delete 失败；
  - validator 与编辑器同时访问 working。
- **建议顺序**：
  1. 完成/回滚 GDAL transaction；
  2. 释放 Feature；
  3. ReleaseResultSet；
  4. 关闭 Layer 相关 cursor；
  5. `GDALClose(dataset)`；
  6. 确认无后台任务；
  7. 再调用 publish。

### 4.2 ArcGIS Pro/Server 对 working 持有 Schema lock

- **等级**：P1
- **触发**：地图、目录窗格、地理处理工具或服务缓存仍连接 working。
- **后果**：文件不能移动、删除或完整验证；锁释放时机受外部程序控制。
- **建议**：ArcGIS 生成应在 store 外完成，完全关闭连接后再导入 working；不要把 work 目录作为交互式长期工程路径。

### 4.3 GDAL transaction commit 被误认为 Store publish

- **等级**：P1
- **触发**：业务在 GDAL CommitTransaction 后向外宣布发布成功。
- **后果**：CURRENT 仍旧，Reader 看不到新数据；或后续 validator/publish 失败。
- **建议**：业务成功点只能以 `publish_state()==PublishedDurable` 为准。

### 4.4 GDAL 驱动版本差异

- **等级**：P2
- **触发**：开发、CI、生产使用不同 GDAL 版本；GDAL 3.11 前后 FileGDB/OpenFileGDB update 路径不同。
- **后果**：字段、索引、关系、曲线和 transaction 能力变化。
- **建议**：记录 GDAL version、driver metadata 和构建选项；真实 GDB 验收必须锁定版本矩阵。

## 5. 文件系统和持久化风险

### 5.1 把 rename 原子性当作崩溃持久性

- **等级**：P0
- **触发**：CURRENT 替换成功后立即删除旧 generation，不检查 root sync。
- **破坏不变量**：崩溃恢复时旧/新 manifest 与 generation 必须同时可推理。
- **当前处理**：`PublishedDurabilityUncertain` 保留新旧版本并阻止 GC。
- **建议**：保留该状态；对每个持久化点做 fault injection。

### 5.2 目录 fsync 不可用或语义弱化

- **等级**：P0/P1
- **触发**：某些平台、挂载、FUSE 或网络文件系统不支持可靠目录同步。
- **后果**：代码表面返回成功，但崩溃后目录项可能丢失或回退。
- **建议**：初始化 capability probe；不能确认时拒绝 Writer，或明确降级为“非 durable 开发模式”，禁止生产使用。

### 5.3 NFS/SMB/云同步目录

- **等级**：P0
- **风险来源**：客户端缓存、机会锁、延迟传播、非一致 rename、锁失效、跨主机时钟和同步工具重写。
- **建议**：默认拒绝；不接受“我们测试过一次可以”的非系统性证明。

### 5.4 跨卷/跨文件系统 promote

- **等级**：P0/P1
- **触发**：work 与 generations 位于不同 mount/volume，rename 退化为复制或失败。
- **当前设计**：work 在 store root 内，理论上应同一文件系统。
- **建议**：启动时比较 device/volume identity；发现跨设备直接拒绝。

### 5.5 Windows path identity 不完整

- **等级**：P1/P2
- **现有处理**：大小写折叠、canonical path。
- **剩余坑**：UNC、mapped drive、junction、8.3 short path、volume GUID path、不同大小写敏感目录配置。
- **建议**：使用 handle-based final path + volume serial/file ID 作为辅助 store identity；测试 junction 和 UNC alias。

### 5.6 POSIX bind mount/hard path alias

- **等级**：P1/P2
- **触发**：同一目录通过 bind mount 或不同 mount namespace 访问。
- **建议**：记录 device/inode；文档说明 canonical string 不能解决所有跨 namespace alias。

## 6. CoW 和容量风险

### 6.1 CoW 成功后后续 ENOSPC

- **等级**：P1
- **触发**：初始 clone 几乎不占空间，但编辑修改大量块、重建 `.spx/.atx`、写临时文件或 fsync 时空间耗尽。
- **误区**：clone 成功 = 事务所需空间已准备。
- **建议**：
  - 记录 clone 前后 free space；
  - 按最坏 FullCopy + 修改放大估算容量；
  - ENOSPC 测试覆盖 clone 后、编辑中、validator 中、sync 中和 CURRENT tmp 阶段。

### 6.2 单文件 CoW 失败导致整体 FullCopy 语义模糊

- **等级**：P2
- **问题**：如果前几个文件已 reflink、后一个失败，是否删除目标并全量重建？最终报告 `FullCopy` 是否意味着全部文件都是真复制？
- **建议**：文档和实现明确：
  - 混合 clone 是否允许；
  - 失败时是否清空重做；
  - copy mode 是“有效结果”还是“是否发生过 fallback”；
  - 日志记录每文件失败原因或至少首个原因。

### 6.3 稀疏文件、xattr、ACL、时间戳差异

- **等级**：P2
- **风险**：FullCopy 或 clone 可能对 sparse extent、extended attributes、ACL、flags、birthtime 的保留不同。
- **建议**：定义哪些元数据属于 FileGDB 正确性；测试源和 working 的权限、大小、稀疏性和扩展属性。

### 6.4 长 Reader 导致磁盘持续增长

- **等级**：P1
- **触发**：每次发布都保留旧 generation，最老 Reader 数小时或数天不释放。
- **建议指标**：
  - active generation count；
  - pinned generation count；
  - oldest lease age；
  - bytes retained by leases；
  - GC last error；
  - free space threshold。

## 7. Validator 风险

### 7.1 抽样被误认为全量证明

- **等级**：P1
- **触发**：只抽样少量 FID/geometry，却向业务承诺整个 GDB 正确。
- **建议**：文档列出每个 profile 的覆盖范围；关键发布可用全扫描或业务 checksum。

### 7.2 只验证结构，不验证业务语义

- **等级**：P1
- **例子**：
  - 记录可读但域值非法；
  - relationship 目标缺失；
  - subtype 默认值错误；
  - extent 过期；
  - 空间索引可解析但漏记录；
  - attribute index collation 与实际过滤不一致。
- **建议**：区分 structural validator、query-equivalence validator、business validator。

### 7.3 未识别高级能力时静默通过

- **等级**：P1
- **触发**：GDB 含关系、栅格、曲线、64-bit OID 等，validator 未检查也未告警。
- **建议**：先做 capability scan；未知对象在 strict profile 下 fail closed，在 permissive profile 下显式 warning 并记录未验证列表。

### 7.4 Validator 自身 Reader 与外部编辑器并存

- **等级**：P1
- **触发**：外部进程仍写 working，validator fresh reopen 同时读取。
- **后果**：校验结果不是稳定快照。
- **建议**：publish 前必须建立 working exclusive ownership；仅“句柄关闭建议”不够，未来需外部锁检测。

### 7.5 索引解析成功但查询不等价

- **等级**：P1/P2
- **建议测试**：对每个索引规则比较 index plan 与 forced scan 的 FID 集合，不能只检查 parser 返回 true。

## 8. CURRENT 和恢复风险

### 8.1 CURRENT 指向存在但损坏的 generation

- **等级**：P0/P1
- **当前 open**：主要确认目标存在；是否每次 open 都做完整 validator 需明确。
- **风险**：磁盘静默损坏或外部篡改后，目录存在但不可读。
- **建议**：支持快速 store integrity check；生产启动可配置 active generation validation level。

### 8.2 自动清理 stale work 误删人工调查证据

- **等级**：P1/P2
- **触发**：崩溃后 `open()` 立即删除 work，导致无法复盘。
- **建议**：
  - 正常模式可清理；
  - recovery/forensic 模式先隔离到 quarantine；
  - 日志记录删除内容和原因；
  - durability uncertain 下禁止清理。

### 8.3 孤儿 generation 的定义不清

- **等级**：P1
- **问题**：不是 CURRENT 且无本进程 lease，不代表没有外部进程使用，也不代表不是故障恢复候选。
- **建议**：在仅同进程支持的前提下可 GC，但文档必须强调外部访问不受保护；未来跨进程后需重写 GC 协议。

### 8.4 recover 的业务回滚边界

- **等级**：P1
- **问题**：技术恢复只确认 CURRENT 指向和持久化，不代表业务认可新 generation。
- **建议**：区分 durability recovery 与 business rollback；`recover()` 不应自动选择“看起来最新”的其他 generation。

## 9. FID、记录和索引语义风险

### 9.1 依赖 FID 连续

- **等级**：P1/P2
- **触发**：业务按 `1..row_count` 遍历；遇到删除孔洞、REPACK 或 sparse OID。
- **建议**：通过实际 row/FID 映射读取，不承诺稠密性。

### 9.2 把 row count、active count、max FID 混为一谈

- **等级**：P1
- **建议**：validator 和日志分别输出 physical slots、active records、scan count、max logical FID、deleted slots。

### 9.3 REPACK 改变物理布局

- **等级**：P2
- **风险**：外部缓存 row offsets、tablx 位置或 mmap 指针跨 generation 复用。
- **建议**：所有底层 offset 只在单 generation/单打开生命周期有效。

### 9.4 64-bit ObjectID 截断

- **等级**：P0/P1
- **触发**：内部接口或测试默认 32-bit；大 OID 被截断、符号扩展或转换失败。
- **建议**：能力扫描；不支持时 fail-fast；全链路类型审计和边界测试。

## 10. 几何风险

### 10.1 曲线折线化结果与 GDAL/ArcGIS 不同

- **等级**：P1/P2
- **原因**：容差、最大弦长、角度、精度网格和闭环策略不同。
- **建议**：文档标明“degraded/linearized”；validator 可同时检查原始 geometry type 和输出策略。

### 10.2 MultiPatch 被当作 Polygon

- **等级**：P1
- **后果**：表面拓扑、法线、part type 和三维语义丢失。
- **建议**：当前明确不支持原生写入；Reader 标记 degraded，不静默降为普通 Polygon 业务等价物。

### 10.3 WKB 有效但 precision metadata 错误

- **等级**：P1
- **建议**：把 XY/Z/M resolution、tolerance、origin 和 spatial reference 元数据纳入扩展 profile。

## 11. API 和错误处理风险

### 11.1 只看 publish() bool

- **等级**：P0/P1
- **触发**：`false` 后统一 abort/retry。
- **后果**：在 CURRENT 已切换但 durability uncertain 时误删新版本或重复发布。
- **当前保护**：`published()` 和 `publish_state()`。
- **建议**：示例必须使用状态枚举；考虑废弃歧义 bool 或提供结果对象。

### 11.2 stale error

- **等级**：P2
- **问题**：成功操作后仍读到上次错误会误报。
- **当前修复**：若已清理错误，应保持回归测试。

### 11.3 析构 abort 的失败不可见

- **等级**：P1/P2
- **触发**：事务未显式 abort，析构清理失败。
- **后果**：残留 work，无错误处理路径。
- **建议**：生产代码显式 abort；析构只做 best-effort 并记录不可忽略日志。

### 11.4 error string 不足以机器处理

- **等级**：P2/P3
- **建议**：引入阶段化错误码：Clone、EditClose、Validate、SyncCandidate、Promote、ManifestWrite、ManifestReplace、RootSync、GC、Recover。

## 12. 可观测性风险

当前若只返回 bool/string，很难回答：

- 哪个 generation 正在被谁持有；
- 为什么 GC 没有发生；
- 本次是 CoW 还是 FullCopy；
- 失败在 CURRENT 前还是后；
- store 是否处于 uncertain；
- 哪个 validator rule 失败；
- 是否检测到未支持能力。

建议最少输出：

```text
store_id
current_generation
writer_transaction_id
working_generation
copy_mode/fallback_reason
publish_phase
publish_state
active_reader_count
oldest_reader_age
pinned_generations
validator_profile
unsupported_capabilities
filesystem_type/device_id
free_space_before/after
GC result
```

## 13. 代码审查检查表

每次修改必须回答：

1. 是否可能修改已发布 generation？
2. 是否可能在 CURRENT 切换后返回 NotPublished 语义？
3. 是否可能在 uncertain 状态删除旧 generation？
4. 是否可能绕过进程内 Writer gate？
5. 路径是否可能逃逸、symlink/junction alias 或跨设备？
6. 新句柄是否在 publish/refresh 前关闭？
7. 错误是否保留主因并追加清理错误？
8. validator 新规则是结构证明还是业务证明？
9. 新能力是否需要 capability profile 和明确不支持声明？
10. Windows、Linux、macOS 的文件系统语义是否分别验证，而非只编译？

## 14. 结论

当前架构最大的坑不是 generation/CURRENT 思路本身，而是使用方很容易把它当成“普通 GDB 的透明增强”。生产正确性依赖协议完整执行。凡是绕过 Store、跨进程、远程文件系统、外部锁未释放、高级 GDB 对象未验证和容量未规划的场景，都必须显式拒绝或降级标记，不能依靠调用方自行猜测。
