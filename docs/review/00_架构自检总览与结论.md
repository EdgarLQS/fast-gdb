# VersionedGdbStore 架构自检总览与结论

- **审查标签**：@深度研究
- **日期**：2026-07-22
- **适用实现**：`agent/versioned-gdb-store`
- **审查范围**：Reader snapshot、单 Writer、working clone、validator、CURRENT publication、durability、recovery、generation GC
- **外部对照**：GDAL/OGR OpenFileGDB、GDAL RFC 54、ArcGIS File Geodatabase locking、Linux/Windows/macOS 文件系统接口
- **结论等级**：Implemented / Formal acceptance blocked

## 1. 执行结论

VersionedGdbStore 当前实现不是对 GDAL/OpenFileGDB 原地编辑模型的简单封装，而是在 FileGDB 之上增加了一套独立的**不可变版本发布协议**：

```text
CURRENT
   ↓
generations/gen-N.gdb     ← Reader snapshot

current generation
   ↓ clonefile/FICLONE/FullCopy
work/work-gen-(N+1).gdb   ← 外部编辑器或 GDAL 只修改这里
   ↓ fresh reopen validation
   ↓ file/directory durability barriers
   ↓ promote
   ↓ atomic CURRENT replacement
generations/gen-(N+1).gdb
```

它最有价值的能力不是字段级写入，而是：

- Writer 永远不修改 Reader 正在持有或 mmap 的已发布文件；
- 发布前后同时允许旧 Reader 和新 Reader 看到不同但各自完整的 generation；
- CURRENT 是唯一活跃版本事实来源；
- 切换前失败不破坏当前版本；
- 切换后持久化失败被显式建模为 `PublishedDurabilityUncertain`；
- 旧 generation 的删除受 Reader 租约和持久性状态约束。

从架构方向看，这套设计是合理的，并且比“原地修改后希望 Reader 不受影响”更容易给出清晰状态机。但当前实现的正确性建立在一组非常严格的前提上。最重要的不是再扩展 API，而是把这些前提变成**文档、运行时检测、测试门禁和运维约束**。

## 2. 当前架构的准确定位

### 2.1 它是什么

VersionedGdbStore 是：

- 一个 FileGDB 完整目录的版本仓库；
- 一个同进程 Reader snapshot 协议；
- 一个同进程单 Writer 协议；
- 一个完整 generation 的验证、发布和恢复协议；
- 一个基于本地文件系统原子命名替换的发布器。

### 2.2 它不是什么

它不是：

- GDAL/OpenFileGDB 的字段级编辑 API 替代品；
- ArcGIS FileGDB 全部数据模型能力的兼容层；
- 跨进程或跨主机数据库事务系统；
- WAL、MVCC 或多版本数据库引擎；
- 对网络文件系统、对象存储或云同步目录的通用发布器；
- 自动解决多个 Writer 冲突、合并和选主的协调系统。

### 2.3 最容易产生的错误心智模型

错误理解：

> “VersionedGdbStore 管理的是一个普通 `.gdb`，外部程序仍然可以直接打开这个 `.gdb`，所有并发和恢复保证依然成立。”

正确理解：

> “VersionedGdbStore 管理的是 `store root + CURRENT + generations + work` 组成的协议。只有经该协议获取 snapshot 或 working path 的访问，才属于受支持行为。”

## 3. 核心不变量

以下不变量必须同时成立；任一被破坏，架构保证都不再成立。

### 3.1 已发布 generation 不可变

- `generations/gen-*.gdb` 发布后禁止任何原地修改；
- Reader 可以长期持有该路径；
- Writer 只能修改 `work/work-gen-*.gdb`；
- validator 只读重开候选；
- 发布完成后不能在新 generation 内“补修一个索引”或“顺手改元数据”。

### 3.2 CURRENT 是唯一活跃版本事实来源

- 不根据目录名最大值、时间戳或创建时间猜测最新版本；
- 不允许外部调用方长期缓存“当前 generation 路径”作为稳定业务入口；
- `open()` 和 `recover()` 必须从 CURRENT 开始推理；
- CURRENT 非法或指向缺失目标时必须 fail closed。

### 3.3 Reader snapshot 覆盖所有派生资源

Snapshot 必须比以下对象活得更久：

- `GdbCatalog`；
- `CatalogResolver`；
- `QueryEngine`；
- cursor；
- 文件描述符或 HANDLE；
- mmap；
- 任何异步任务中保存的 table/index/geometry reader。

只保存 `snapshot.path()` 然后提前销毁 snapshot，会绕过 generation 租约并导致旧版本可能被 GC。

### 3.4 Writer 必须是协议内唯一 Writer

当前唯一性仅覆盖：

- 同一进程；
- 经规范化后识别为同一 store root 的实例；
- 通过 `begin_write()` 创建的事务。

它不覆盖：

- 另一个进程；
- ArcGIS Pro、ogr2ogr、QGIS 或自定义程序直接打开 generation/work；
- 网络共享上的另一台机器；
- 手工复制、移动或删除目录。

### 3.5 原子可见性与崩溃持久性必须分离

- CURRENT 原子替换解决“观察者不会看到半行 manifest”；
- 文件和目录持久化屏障解决“崩溃后命名和数据是否仍存在”；
- 两者不能用一个 `bool` 混淆；
- `PublishedDurabilityUncertain` 是必要状态，而不是异常细节。

### 3.6 GC 必须保守

只有同时满足以下条件才可删除旧 generation：

1. 不是 CURRENT；
2. Reader 租约为零；
3. 不处于 durability uncertain；
4. 没有活动 Writer/recovery；
5. 删除错误能够传播和诊断。

## 4. 与 GDAL/OpenFileGDB 的根本差异

| 维度 | VersionedGdbStore | GDAL/OpenFileGDB 典型模型 |
|---|---|---|
| 更新对象 | working generation | 目标 `.gdb` 本体 |
| 提交单元 | 完整 FileGDB generation | 数据集级模拟事务或原地更新 |
| Reader 可见性 | snapshot 固定版本 | 无 generation snapshot 协议承诺 |
| Writer 并发 | 同进程单 Writer | 并发 update 行为未指定或不建议 |
| 回滚 | 删除未发布 working | 恢复事务备份或驱动内部处理 |
| 发布 | CURRENT 原子切换 | 无 CURRENT 上层 manifest |
| 崩溃状态 | 显式 durability uncertain | 由驱动、锁文件和文件系统行为决定 |
| CoW | 发布协议的性能优化 | 非 GDAL FileGDB 事务语义组成部分 |
| Validator | 发布前强制 fresh reopen | 驱动打开/操作成功不等价于自定义发布验收 |
| 高级 GDB 语义 | 只覆盖明确实现和校验的子集 | OpenFileGDB 支持更广的关系、层级、索引和类型能力 |

因此，fast-gdb 不应在宣传或文档中表述为“比 GDAL 更完整的 FileGDB Writer”。更准确的表述是：

> VersionedGdbStore 用额外复制、校验和持久化成本，换取同进程服务中的 Reader 连续可见性、不可变发布和更清晰的恢复边界。

## 5. 风险分级

### 5.1 P0：会直接破坏正确性或造成数据不可恢复

#### P0-1 外部进程绕过协议直接修改 generation

后果：

- 已发布不可变假设失效；
- 旧 Reader 读取到被修改文件；
- validator 的发布证明失效；
- GC 和恢复无法判断 generation 是否可信。

要求：文档必须写成“明确不支持”，未来建议增加进程级 sidecar lock 或只读权限强化。

#### P0-2 跨进程 Writer

当前进程内 registry 无法阻止另一进程同时 begin/write/publish。两个进程可能从同一 CURRENT 派生 working，然后互相覆盖 CURRENT，造成 lost update、孤儿 generation 和错误 GC。

要求：未实现跨进程锁前必须明确拒绝多进程写入部署。

#### P0-3 durability uncertain 后继续 GC 或再次写入

如果 CURRENT 替换已可见但根目录持久化失败，崩溃后旧 CURRENT 可能重新出现。此时若旧 generation 已删除，将产生 manifest 指向缺失目录。

要求：当前实现已通过状态阻止 GC/新 Writer；必须保持该约束并做故障注入测试。

#### P0-4 在不可靠网络文件系统部署

NFS/SMB/FUSE/云同步目录可能弱化：

- rename 可见性；
- 目录持久化；
- 缓存一致性；
- 路径身份；
- 文件锁；
- 删除与打开句柄的时序。

要求：没有专门验证前一律定义为不支持，而不是“性能较差”。

### 5.2 P1：高概率导致生产事故、不可用或容量失控

#### P1-1 CoW 成功被误认为容量已预留

Reflink 只共享旧数据块。后续修改、索引重建和刷盘仍可能 ENOSPC。

要求：日志记录实际 clone path、fallback 原因、事务各阶段空间；文档明确“CoW ≠ capacity reservation”。

#### P1-2 长生命周期 Reader 阻止 GC

长查询、泄漏 cursor、缓存 QueryEngine、线程池任务和未关闭 mmap 都会延长 snapshot，导致旧 generation 累积。

要求：提供租约年龄、generation 引用数和磁盘占用指标；设置业务级最大 snapshot 年龄告警。

#### P1-3 publish 前未关闭 GDAL Dataset/Layer/Feature 句柄

外部编辑器可能延迟 flush、持有锁文件、缓存 schema 或继续写。validator 可能看到不完整状态，Windows rename/delete 也可能失败。

要求：调用方必须显式关闭 Dataset、Layer、Feature、SQL result set、cursor、fd 和 mmap；不能仅依赖析构时机不确定的对象。

#### P1-4 validator 覆盖不足却被当作完整兼容证明

当前 validator 重点覆盖记录、FID、几何和索引结构，但不等于关系类、域、subtype、feature dataset、几何精度、栅格、拓扑、网络数据集等语义完整。

要求：发布能力按 compatibility profile 分档；未知高级能力默认 warning 或 fail closed。

#### P1-5 CURRENT 或 generation 被人工修改

手工修改 CURRENT、删除旧目录、重命名 generation 或使用文件浏览器移动内部文件，会破坏恢复推理。

要求：运维必须只通过受控工具操作；建立 `verify-store/doctor` 检查入口。

### 5.3 P2：会导致性能退化、行为误解或验收缺口

- 任一文件 CoW 失败导致整笔事务报告 FullCopy，性能和空间峰值突变；
- Windows path alias 仍可能受 junction、UNC、短路径、映射盘影响；
- POSIX bind mount/device-inode 身份可能超出单纯 canonical string；
- 全树 fsync 在大 GDB 上可能产生明显发布尾延迟；
- 全量 validator 对超大库成本高，抽样 validator 又无法证明全部业务语义；
- `.spx/.atx` 可解析不等于查询结果与 ArcGIS/GDAL 完全一致；
- FID 连续性、删除孔洞、REPACK 后布局不能作为 API 承诺；
- Windows `MoveFileExW` 和 POSIX rename 的行为细节不能只用统一术语概括。

## 6. 当前支持边界

### 6.1 正式设计目标

- 本地可靠文件系统；
- 单进程；
- 多个独立 Reader snapshot；
- 一个 Writer；
- 完整 FileGDB generation 提交；
- 本地 `clonefile`/`FICLONE` 优先，FullCopy 回退；
- publish 前 fresh reopen validator；
- CURRENT 原子切换；
- 同进程 Reader 租约 GC；
- 显式 recover。

### 6.2 明确不支持

- 多进程 Writer；
- 跨进程 Reader 租约与安全 GC；
- 网络文件系统、云同步目录、对象存储；
- 直接编辑 published generation；
- 手工改 CURRENT；
- 稳定暴露 generation 路径给外部系统；
- 字段级 Writer 公共 DSL；
- schema migration；
- savepoint、嵌套、跨 GDB、分布式事务；
- 多 Writer 合并；
- 自动容量预留；
- 旧 API 兼容。

### 6.3 未经证实、应按不支持处理

- 稀疏 64-bit ObjectID；
- 关系类完整保真；
- domain/subtype/contingent values；
- feature dataset 层级与引用完整性；
- topology、network dataset、utility network、parcel fabric；
- 原生曲线写入；
- MultiPatch 完整写入；
- raster/mosaic dataset 发布语义；
- SDC/CDF 或其他压缩数据；
- ZIP/HTTP/VSI 上的 VersionedGdbStore；
- NFS/SMB/FUSE/WSL 跨边界路径；
- ArcGIS 与 GDAL 同时对同一 working GDB 编辑。

## 7. 需要补充的运行时保护

按优先级建议：

1. **跨进程 store lock**：未实现前检测已有 owner 并 fail-fast；
2. **filesystem capability probe**：识别本地/远程/FUSE、目录 sync 能力和 rename 边界；
3. **store doctor**：验证 CURRENT、generation 位置、符号链接、残留 work、只读属性和索引；
4. **capability scanner**：发现关系、域、层级、64-bit OID、曲线、栅格等未验证能力；
5. **lease observability**：输出 generation、租约数、最老租约年龄、GC 阻塞原因；
6. **publication phase metrics**：clone、edit-close、validate、sync-tree、promote、manifest、root-sync、GC；
7. **fault injection seam**：每一个持久化和 rename 阶段可控失败；
8. **manual operation guard**：生成 store metadata/version 文件，并在异常变更时拒绝打开。

## 8. 文档措辞要求

所有面向用户的文档都应重复以下三句话：

> VersionedGdbStore 提供的是 FileGDB 的版本化发布协议，不是 ArcGIS/GDAL 原地编辑语义的透明替代。

> 一致性保证只在所有访问经托管入口、store 位于可靠本地文件系统、且同一时刻只有一个进程负责写入时成立。

> validator 通过只表示仓库当前定义的不变量已满足，不表示 ArcGIS/GDAL 全部高级 geodatabase 语义已完整兼容。

## 9. 当前验收判断

### 已实现

- generation store 布局；
- Reader snapshot；
- 进程内单 Writer；
- 路径规范化；
- CoW/FullCopy；
- fresh reopen validator；
- CURRENT 严格格式；
- 原子切换；
- durability uncertain；
- recovery 和保守 GC；
- latest-only Writer API。

### 尚不能宣布 Accepted

原因不是已知架构错误，而是缺少生产级证据：

- 三平台完整构建/CTest；
- APFS、Btrfs/XFS、ext4、NTFS 实际矩阵；
- Windows manifest replacement 和句柄占用测试；
- ENOSPC、EIO、permission、directory sync、crash-phase 注入；
- 真实复杂 FileGDB，包括关系、域、层级、64-bit OID 和曲线；
- 多进程误用检测；
- 远程文件系统拒绝策略；
- 长 Reader 租约和磁盘增长压力测试；
- 安装包与 API 负向检查的可审计 CI artifacts。

因此状态应继续保持：

```text
Implemented
Formal acceptance blocked
Production deployment requires explicit constraints
```
