# 技术探索与教训

本文档记录了 fast_gdb 项目中的关键技术发现、遇到的 Bug 及修复过程、失败实验的教训，以及性能优化的方法论。

---

## 1. B+ 树分隔符语义（核心发现）

### 1.1 问题

v7 优化中，`query_bbox` 只返回 1 条结果，而 GDAL 组件返回 13 条。

### 1.2 根因

Root 页面的 entry 不是 child 的**最小值**，而是**分隔符**：

```
Root entry[10]: child=12 cx=6 cy=17  → page 12 第一个 entry: cx=5 cy=20 (更小!)
Root entry[11]: child=13 cx=7 cy=15  → page 13 第一个 entry: cx=6 cy=17 (更小!)
Root entry[12]: child=14 cx=8 cy=16  → page 14 第一个 entry: cx=7 cy=15 (更小!)
```

child[i] 的 cx 范围：`entry[i-1].cx < cx <= entry[i].cx`
child[0] 的 cx 范围：`cx <= entry[0].cx`

这意味着 entry[i].raw < query_start **不代表子树没有匹配数据**。

### 1.3 修复

直接翻译 GDAL 源码的 `FindPages` 模式：

```cpp
// 分支页面：GDAL FindPages 逻辑
// Find iLastPageIdx: first entry where cx > q_max_cx
int i_last = static_cast<int>(entry_count);
for (int i = 0; i < static_cast<int>(entry_count); i++) {
    uint64_t v; std::memcpy(&v, page + values_offset_ + i * 8, 8);
    uint32_t cx = static_cast<uint32_t>((v >> 31) & 0x7FFFFFFF);
    if (cx > q_max_cx) { i_last = i; break; }
}

// Find iFirstPageIdx: first entry where cx >= q_min_cx, then use child[i-1]
int i_first = 0;
for (int i = 0; i < static_cast<int>(entry_count); i++) {
    uint64_t v; std::memcpy(&v, page + values_offset_ + i * 8, 8);
    uint32_t cx = static_cast<uint32_t>((v >> 31) & 0x7FFFFFFF);
    if (cx >= q_min_cx) { i_first = (i > 0) ? i - 1 : 0; break; }
}
```

### 1.4 教训

- **B+ 树 entry 是分隔符，不是子树最小值** — 这是 v6→v7 失败的根因
- **直接翻译 GDAL 源码比自己设计逻辑更高效** — v7 失败是因为试图简化，v8 成功是因为完整翻译

## 2. LRU 缓存淘汰 Bug

### 2.1 问题

reused 对象查询结果错误（Local=0, Regional=445, Large=1089 vs fresh 正确值）。

### 2.2 根因

`GdbSpatialIndexParser` 使用 `page_cache_[kMaxDepth]`（4 个 slot）缓存 .spx 页面。`read_page()` 的 slot 选择逻辑有缺陷：

```cpp
// 错误代码
int slot = 0;
for (int i = 0; i < kMaxDepth; i++) {
    if (!page_cache_[i].valid) { slot = i; break; }
}
// 如果 4 个 slot 全满，slot 保持 = 0，总是覆盖 slot 0
```

**影响**：
- reused 场景：同一个 parser 的 cache 在 4 次查询间共享
- 递归 `collect_fids_btree` 遍历时，分支页面被错误覆盖
- 后续 `read_page()` 读到脏数据，FID 丢失

### 2.3 修复

```cpp
struct PageCache {
    mutable uint32_t page_id = 0;
    mutable uint8_t data[kPageSize];
    mutable bool valid = false;
    mutable uint64_t last_used = 0;  // LRU 访问时间戳
};
mutable uint64_t cache_counter_ = 0;  // 单调递增计数器

// read_page() 重写驱逐逻辑
int slot = 0;
uint64_t min_used = UINT64_MAX;
for (int i = 0; i < kMaxDepth; i++) {
    if (!page_cache_[i].valid) { slot = i; break; }
    if (page_cache_[i].last_used < min_used) {
        min_used = page_cache_[i].last_used;
        slot = i;
    }
}
page_cache_[slot].last_used = ++cache_counter_;
```

### 2.4 教训

- **缓存淘汰必须正确实现 LRU**，否则递归遍历时分支页被破坏
- **跨查询缓存需要清理**：在 `query_bbox()` 入口调用 `clear_cache()`

## 3. mmap 优化之旅

### 3.1 瓶颈分析

- `peek_geometry_blob()` 每次调用 2 次 pread()（4 字节头 + ~140 字节数据）
- 10M Large 查询：8.17M 次 peek × 2 = **16.3M 次系统调用**
- 总耗时 5054ms，与 16.3M × 0.31μs 估算完美吻合
- 对比：顺序读 1.4GB 仅需 <100ms → **系统调用开销导致慢 ~50 倍**

### 3.2 mmap 缺点分析

| 缺点 | 严重度 | 对项目的影响 |
|------|:------:|----------------|
| page cache 污染 | 中 | 10M 文件 1.4GB 会占满 page cache，但场景是专用 benchmark，影响有限 |
| 随机访问不如 pread | 低 | FID 已排序，偏移几乎连续，不是随机访问 |
| 小文件 setup 开销 | 低 | 小数据集 2MB，mmap setup ~1ms 可忽略 |
| 平台差异 | 低 | macOS ARM64 完全支持 |
| 不能增量释放 | 低 | 64 位系统 256TB 虚拟地址，1.4GB 微不足道 |
| 调试困难 | 中 | 需做好边界检查 |
| 文件锁定 | 极低 | .gdbtable 是只读数据文件 |

**结论**：在大文件、近似顺序访问、只读、专用 benchmark 场景下，mmap 缺点影响都很小。

### 3.3 实现

```cpp
// gdb_table.h — 新增成员
uint8_t* mapped_data_ = nullptr;  // mmap 映射基址

// gdb_table.cpp — open() 添加 mmap
mapped_data_ = static_cast<uint8_t*>(
    mmap(nullptr, file_size_, PROT_READ, MAP_PRIVATE, fd_, 0));
if (mapped_data_ == MAP_FAILED) mapped_data_ = nullptr;  // 降级到 pread
madvise(mapped_data_, file_size_, MADV_SEQUENTIAL);

// read_at() — 优先用 memcpy
bool GdbTableParser::read_at(uint64_t offset, void* buffer, size_t size) const {
    if (mapped_data_ && offset + size <= file_size_) {
        std::memcpy(buffer, mapped_data_ + offset, size);
        return true;
    }
    // fallback: pread
    ssize_t n = pread(fd_, buffer, size, static_cast<off_t>(offset));
    return n == static_cast<ssize_t>(size);
}

// 析构 — 添加 munmap
if (mapped_data_) munmap(mapped_data_, file_size_);
```

### 3.4 效果

| 指标 | 改造前 | 改造后 | 加速 |
|------|--------|--------|------|
| peek_blob 耗时 (10M Large) | 5055ms | ~160ms | **31×** |
| 总查询耗时 | 6121ms | ~1200ms | **5×** |
| pread 系统调用 | 16.3M 次 | 0 次 | — |

## 4. Phase C 直写器系统表问题

### 4.1 现象

- explorgdb 读回验证：字段解析正确 ✅
- GDAL OpenFileGDB 读取：无法正确读取要素计数 ❌

### 4.2 根因

`a00000000.gdbtable` 系统表未更新。GDB 格式有多个系统表需要同步更新：
- `a00000000.gdbtable` — 主系统表（图层信息、要素计数）
- `a00000000.gdbtablx` — 系统表偏移

### 4.3 状态

⚠️ **待修复**：需要实现 `update_system_tables()` 更新系统表。

### 4.4 教训

- **GDB 格式不是简单的数据文件**，有多个系统表需要同步更新
- **explorgdb 回读验证通过不等于 GDAL 兼容**，需要双重验证

## 5. 自研多层 B+ 树索引的失败

### 5.1 尝试

Phase D 实现了索引构建的核心功能：
- BPlusTreeWriter — 模板化 B+ 树构建（仅单层）
- SpatialIndexWriter — 几何 bbox→网格单元离散化 + 64 位编码
- AttributeIndexWriter — 多类型字段值 B+ 树
- GdbIndexesWriter — .gdbindexes 元数据注册表

### 5.2 限制

| 限制 | 说明 |
|------|------|
| 单层 B+ 树 | 仅支持 < 1000 条目（depth=1，340 条/页） |
| 多层扩展复杂 | depth>1 需要逐层构建分支页，参考 GDAL 实现 |
| 生产质量差距 | ArcGIS Pro 支持 130 亿条目（depth=4） |

### 5.3 决策

- 自研索引代码已删除
- 生产环境使用混合工作流（ArcGIS Pro）或 GDAL SQL 方案

### 5.4 教训

- **不要重复造轮子**：GDAL/ArcGIS Pro 已经有成熟的多层 B+ 树实现
- **研究 vs 生产要分离**：实验性代码应独立管理，生产代码用成熟方案
- **单层 B+ 树只适合小数据集**（< 1000 条），大数据集必须用多层

## 6. 零拷贝顺序扫描设计

### 6.1 关键设计

- **mmap 天然支持零拷贝**：指针直接访问映射内存
- **配合零堆分配**：RowBuffer 复用内部 buffer，跨行无 malloc/free
- **消除 FieldValue variant 构造**：用 FieldRef 指向原始字节
- **消除 string 堆分配**：返回 string_view
- **预分配 FieldRef 数组**：避免每行 vector 分配

### 6.2 效果

| 规模 | GDAL (ms) | explorgdb seq scan (ms) | 加速比 |
|:----:|:---------:|:----------------------:|:------:|
| 100K | 124 | **10.5** | **12x** |
| 10M | 9,258 | **1,042** | **9x** |

## 7. 性能优化方法论

### 7.1 先测量，后优化

使用 `WriteTiming` 结构体记录每个阶段的耗时：

```cpp
struct WriteTiming {
    double create_layer_ms = 0;
    double toNative_ms = 0;
    double setGeometry_ms = 0;
    double createFeature_ms = 0;
    double destroyFeature_ms = 0;
    double flush_overhead_ms = 0;
    double total_ms = 0;
    int feature_count = 0;
};
```

### 7.2 失败实验也要记录

| 实验 | 结果 | 教训 |
|------|------|------|
| LRU Cache 16→64 slot | ±0% 无效果 | mmap 已优化文件读取，缓存查找开销抵消命中率提升 |
| Phase D 自研多层 B+ 树 | 单层限制 <1000 条 | GDAL/ArcGIS Pro 方案更优，转向混合工作流 |

### 7.3 瓶颈分析

**10M Large 场景瓶颈分布**（优化前）：

| 阶段 | 耗时 | 占比 |
|------|------|------|
| q_bbox (B+ 树查询) | 790.9ms | 13% |
| peek_blob (读取几何 blob) | 5054.9ms | **83%** |
| peek_bbox + intersect | 192.7ms | 3% |

**结论**：peek_blob 是主要瓶颈（83%），优化 I/O 是首要任务。

### 7.4 优化优先级

1. **I/O 优化**（mmap）：peek_blob 5000ms → 160ms（31x）
2. **算法优化**（bitset 去重 + 排序）：q_bbox -51%
3. **微优化**（预计算倒数、reserve）：小幅提升
4. **架构优化**（Phase C 直写器）：写入 28-36x 加速

## 8. 两种不同的坐标解码公式

FileGDB 几何 blob 中有**两种不同的 varuint 解码方式**：

### 8.1 点坐标

```
real_coord = (raw_varint_cumulative) / scale + origin
```

对应 `decode_coord()` 中的 `(raw - 1) / scale + origin`，用于存储每个点的实际坐标。

### 8.2 包围盒坐标

```
real_coord = raw_varuint / scale + origin
```

对应 `decode_bbox_coord()` 中的 `raw / scale + origin`，用于存储几何的 min/max bbox（4 个 varuints）。

**这是 GDAL `filegdbtable.cpp` 中的实现方式。**

## 9. 损坏的 field descriptor

测试数据中的几何字段 descriptor 存储了 `xorig = yorig = -2147483647`（INT_MIN sentinel 值）。

### 9.1 影响

- **空间索引 cell 计算**：需要 clamp 为 0.0 才能正确计算 cell 坐标
- **几何坐标解码**：需要使用**原始值** `-2147483647`，因为 GDAL 的公式是 `raw/scale + xorig`

### 9.2 微妙的平衡

```
(-2147483647) + (raw / 10000) ≈ real_coordinate
```

当 xorig 为 INT_MIN 时，`raw/scale` 是一个很大的正数，加上 INT_MIN 后得到正确的 Albers 投影坐标。

## 10. 读写分离重构的决策

### 10.1 背景

explorgdb 根目录混杂了读取器代码和公共类型（24 个文件），writer 依赖 GDAL，varint 代码重复。

### 10.2 目标结构

```
src/edgar/explorgdb/
├── common/     ← 读写共享的基础设施（纯 C++17，无外部依赖）
├── reader/     ← GDB 读取器（纯 C++，不依赖 GDAL）
└── writer/     ← GDB 写入器（纯 C++，不依赖 GDAL）
```

### 10.3 关键变更

1. **文件迁移**：binary_reader, varint, utf16, ole_date → common/
2. **varint 统一**：删除 writer/varint_encoder.h，合并到 common/varint.h
3. **writer 去 GDAL 依赖**：移除 create_new()，保留 open_existing()
4. **CMake 三库分离**：explorgdb_common_lib, explorgdb_reader_lib, explorgdb_writer_lib

### 10.4 依赖关系

```
common/     ← 无依赖（纯 C++17 标准库）
reader/     → common/
writer/     → common/
```

三个库全部纯 C++，不依赖 GDAL。只有测试运行器和 CLI 工具需要 GDAL。

### 10.5 教训

- **读写分离是正确方向**：消除耦合，依赖清晰
- **纯 C++ 库更易维护**：不依赖 GDAL 的 reader/writer 可独立编译测试
- **重构不改变业务逻辑**：只移动文件 + 更新 include

## 11. GDAL SQL 索引创建的设计决策

### 11.1 方案选择

| 方案 | 实现方式 | 优点 | 缺点 | 工作量 |
|------|---------|------|------|--------|
| A | GDAL C API | 简单直接，代码量少 | 依赖 GDAL | 4-5 小时 |
| B | GDAL C++ API | 面向对象 | 比 A 稍复杂 | 6-8 小时 |
| C | 移植到 explorgdb | 不依赖 GDAL | 工作量大（2-3 天） | 16-24 小时 |

**选择方案 A**：最简单高效，1-2 小时完成核心功能。

### 11.2 关键发现

GDAL OpenFileGDB 驱动已经完整实现了多层 B+ 树索引创建功能，通过 SQL 接口可直接调用。

### 11.3 SQL 错误是装饰性的

**现象**：执行 `CreateSpatialIndex` 时输出警告：
```
[IndexCreator] Warning: CREATE SPATIAL INDEX SQL failed
  Error: SQL expression not supported by this driver
  Note: OpenFileGDB auto-creates indexes when features are written
```

**原因**：GDAL OpenFileGDB 驱动不支持通过 SQL 显式创建索引，但会在写入要素时自动触发索引创建。

**处理**：函数实现已处理此场景 — SQL 失败后检查文件系统，如果 `.spx`/`.atx` 文件存在则返回 true。

### 11.4 教训

- **充分利用已有生态**：GDAL 已有成熟实现，无需重复造轮子
- **方案选择要权衡**：方案 A 最简单，4-5 小时完成，效果与方案 C 相同
- **理解驱动的隐藏行为**：OpenFileGDB 自动创建索引，SQL 只是触发器

## 12. 总结

### 12.1 核心技术发现

1. **B+ 树 entry 是分隔符，不是最小值** — 直接翻译 GDAL 源码比自己设计更高效
2. **mmap 在大文件场景下优势巨大** — 消除 16.3M 次系统调用，31x 加速
3. **零拷贝 + 零堆分配是性能关键** — seq_scan 比 GDAL 快 9-12x
4. **GDB 格式有多个系统表** — explorgdb 回读通过不等于 GDAL 兼容

### 12.2 失败教训

1. **LRU 缓存必须正确实现** — 否则递归遍历时分支页被破坏
2. **不要重复造轮子** — 自研多层 B+ 树不如用 GDAL/ArcGIS Pro
3. **单层 B+ 树只适合小数据集** — 大数据集必须用多层
4. **缓存扩大不一定有效** — LRU 16→64 slot 实验证明无效果

### 12.3 优化方法论

1. **先测量，后优化** — 用 WriteTiming 结构体记录每阶段耗时
2. **瓶颈分析优先** — peek_blob 占 83%，优化 I/O 是首要任务
3. **失败实验也要记录** — 避免重复尝试
4. **读写分离是正确方向** — 消除耦合，依赖清晰
