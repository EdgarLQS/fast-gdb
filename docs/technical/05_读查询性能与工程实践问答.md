## 第一章 读查询性能分析：为何比 GDAL 快

### 1.1 基准测试概览

以下数据来自 `docs/technical/01_性能基准与优化.md`，基于 macOS (Apple Silicon)、GDAL 3.9.3、10 万要素 Polygon + 4 属性字段的受控合成数据。

| 查询类型 | 规模 | explorgdb | GDAL | 加速比 |
|----------|:----:|:---------:|:----:|:------:|
| 全表顺序扫描 | 100K | 10.5 ms | 124 ms | **12.0x** |
| 全表顺序扫描 | 10M | 1,042 ms | 9,258 ms | **8.9x** |
| 空间查询（1% 窗口） | 100K | 0.97 ms | 15.61 ms | **16.0x** |
| 空间查询（0.1% 窗口） | 10M | 0.86 ms | 1,529 ms | **1,778x** |
| 属性范围查询（>8M） | 100K | — | — | **17.6x** |
| 属性范围查询（<2M） | 100K | — | — | **17.5x** |

**关键趋势**：随着数据规模增大，explorgdb 的优势从 ~10x 扩大到三个数量级。GDAL 的查询时间与数据规模呈线性关系（O(N)），而 explorgdb 的 B+ 树索引查询复杂度为 O(log N + K)，小窗口查询几乎恒定。

### 1.2 根因分析：四维分解

explorgdb 相对于 GDAL 的性能优势可分解为四个维度：

| 维度 | GDAL 的做法 | explorgdb 的做法 | 贡献占比 |
|------|:-----------|:-----------------|:--------:|
| I/O 层 | 每个要素一次 pread() 系统调用 | mmap 内存映射，零系统调用 | ~50% |
| 对象创建 | 每个要素创建 OGRFeature 对象（堆分配） | 零拷贝 FieldRef 指向 mmap 内存 | ~30% |
| 抽象层 | 5-7 层虚函数调用链 | 内联模板 + 直接函数调用 | ~15% |
| 索引策略 | B+ 树全量加载 | B+ 树按需导航 + LRU 缓存 | -5% |

**核心洞察**：GDAL 每个要素都支付固定开销（对象创建 + 系统调用），而 explorgdb 将两者降至零。随着结果集从 1,800 个扩大到 8.17M 个，累计固定开销将差距从 1x 放大到 8x。

#### 1.2.1 I/O 层：mmap vs pread

GDAL 的 OpenFileGDB 驱动使用 `pread()` 进行定位读取。在大规模查询中，这产生了 **1,630 万次**系统调用，每次调用都涉及用户态/内核态切换、权限检查、文件偏移更新。

explorgdb 使用 `mmap()` 将整个文件映射到虚拟内存地址空间：

- 文件数据按需通过缺页中断加载到物理内存
- 后续访问直接操作内存地址，**零系统调用**
- 页面缓存由 OS 内核管理，多进程共享

**效果**：`peek_blob()` 操作从 5,055ms 降至 160ms（**31x** 加速），总查询时间从 6,121ms 降至 1,200ms（**5x** 加速）。

**mmap 的潜在缺点**：
- 页缓存污染：不适合大文件小范围随机访问
- 跨平台差异：Windows 上需要 `CreateFileMappingW` + `MapViewOfFile`
- 对于 fast-gdb 的查询模式（连续读取或 B+ 树索引导航），这些缺点不构成问题

#### 1.2.2 对象创建：零堆分配 vs OGRFeature

GDAL 的查询流程：

```
pread() → 分配 OGRFeature → 分配 OGRGeometry → 分配 OGRField[] → 填充值
                                                                ↓ 用户使用
                                    ↓ 遍历全部 8.17M 个要素
                            用户调用 DestroyFeature() 释放
```

每次迭代都涉及：
- OGRFeature 堆分配（构造函数 + 虚函数表初始化）
- OGRGeometry 堆分配（几何类型分发）
- OGRField 数组分配（字段类型检查 + 值拷贝）
- 最终释放（析构函数 + 内存回收）

explorgdb 的零拷贝顺序扫描：

```
mmap 映射 → FieldRef 指向 mmap 中的原始字节 → 用户直接访问
```

- 无 memcpy
- 无 FieldValue 变体构造
- 无字符串堆分配
- 无 OGR 对象创建

**效果**：顺序扫描每要素仅 0.10-0.11μs，而 GDAL 为 0.93-1.24μs。

#### 1.2.3 抽象层：内联分发 vs 虚函数

GDAL 的调用链：

```
GDALDataset::GetLayer() → OGRLayer::GetNextFeature() → OGRFeature::GetField()
→ OGRFieldDefn::GetType() → OGRGeometry::exportToWkt() → ...
```

每层调用都涉及：
- 虚函数表查找（vtable 间接跳转）
- 分支预测失效风险
- 编译器无法内联

explorgdb 的调用链：

```
GdbTableParser::sequential_scan() → FieldRef::as_int32() → 直接读取内存
```

- 编译时已知类型
- 内联模板消除函数调用开销
- 分支预测友好

#### 1.2.4 索引策略：B+ 树导航

这是唯一一个 GDAL 在某些维度上可能更快的方面。GDAL 的 B+ 树在小数据量下索引查找更快（-5% 贡献），但 explorgdb 的 B+ 树按需导航设计在大数据量下展现出爆炸性优势：

- 0.1% 窗口 10M 数据：**1,778x** 加速（explorgdb 0.86ms vs GDAL 1,529ms）
- 原因：GDAL 的 B+ 树查询时间随数据规模线性增长，而 explorgdb 的 B+ 树 + LRU 缓存在小窗口下近乎恒定

### 1.3 优化技术详解

#### 1.3.1 mmap 内存映射

```
[原始文件] → mmap() → [虚拟内存地址]
                            ↓
                      FieldRef 直接指向
                      mmap 中的原始字节
```

- 消除了 16.3M 次 pread() 系统调用
- 使用 `madvise(MADV_SEQUENTIAL)` 优化页面预取
- LRU 缓存（16 槽）缓存 B+ 树页面，减少索引页面的缺页中断

#### 1.3.2 B+ 树按需导航

最早版本将整个 B+ 树加载到内存（37M 条目，~1.2GB）。优化后改为：

```
读取 B+ 树 trailer（22 字节）→ 定位根页面 → 按需导航到目标叶子页面
                                                              ↓
                                                LRU 缓存最近使用的页面
```

- 修复了一个关键 bug：叶子页面链表遍历导致 2,187 万次页面读取
- 按需导航避免了全量加载的 1.2GB 内存占用

#### 1.3.3 零拷贝顺序扫描

```cpp
// 伪代码示意
void sequential_scan(const uint8_t* mmap_base, size_t size) {
    const uint8_t* cursor = mmap_base + header_size;
    while (cursor < mmap_base + size) {
        FieldRef ref(cursor);  // 指向 mmap 中的原始字节，无拷贝
        process(ref);          // 用户直接使用
        cursor += ref.total_size();
    }
}
```

- 消除了每要素的 memcpy
- 消除了 FieldValue 变体构造
- 消除了字符串堆分配

#### 1.3.4 预计算倒数

将坐标解码中的除法替换为乘法：

```cpp
// 优化前
double decoded = (raw - 1) * scale + origin;  // 除法指令

// 优化后
double decoded = (raw - 1) * inv_scale + origin;  // 乘法指令
```

- 点查询：15.4ms → 7.5ms（-51%）
- 预计算在坐标系初始化时完成

#### 1.3.5 LRU 缓存

| 缓存大小 | 点查询耗时 | 改善 |
|:--------:|:----------:|:----:|
| 4 槽 | 18.0 ms | 基线 |
| 16 槽 | 11.8 ms | -34% |
| 64 槽 | 11.8 ms | 0%（无进一步改善） |

- 64 槽无改善：mmap 已优化文件读取，缓存查找开销抵消了命中率提升
- 最终使用 16 槽

#### 1.3.6 位集去重

B+ 树多层级网格查询可能产生重复 FID。优化前后：

```cpp
// 优化前：std::sort + std::unique
std::sort(fids.begin(), fids.end());
auto last = std::unique(fids.begin(), fids.end());

// 优化后：bitset 去重
std::vector<bool> seen(max_fid + 1);
for (auto fid : fids) { if (!seen[fid]) { seen[fid] = true; ... } }
```

- 空间包围盒查询：659ms → 322ms（-51%）
- 去重后必须保持排序以维持空间局部性

#### 1.3.7 微优化

- **UTF-16 转换**：`reserve(char_count * 3)` 预分配缓冲区
- **字符串预分配**：避免多次堆分配增长
- **UUID 固定缓冲区**：栈上分配，避免堆分配
- **WKT 预计算长度**：`reserve()` 避免多次增长

### 1.4 为什么随数据量增大差距扩大

| 结果集大小 | GDAL 固定开销 | explorgdb 固定开销 | 差距 |
|:----------:|:-------------:|:------------------:|:----:|
| 1,800 个 | 1,800 × 0.93μs = 1.67ms | 1,800 × 0.10μs = 0.18ms | 1x |
| 8.17M 个 | 8.17M × 1.24μs = 10,130ms | 8.17M × 0.11μs = 898ms | 8x |

GDAL 的固定开销包括：
- 每次 pread() 系统调用（~1-2μs）
- OGRFeature 对象构造/析构（~0.3μs）
- 虚函数分发（~0.1μs）

这些开销在 1,800 个要素时微不足道，但在 8.17M 个要素时累积到数秒。

### 1.5 总结

| 维度 | 结论 |
|------|------|
| 性能差距来源 | 主要是 I/O 层（mmap vs pread）和对象创建层（零堆分配 vs OGRFeature） |
| 差距随规模变化 | 固定开销累积，小结果集 ~1x，大结果集 ~8x+ |
| 加速极限 | 取决于查询窗口大小，窗口越小加速比越大 |
| 适用场景 | 大量数据的全表扫描或小窗口空间查询 |
| 不适用场景 | 小数据量（<10K）时差异不大 |

### 1.6 没有索引时怎么处理？

当 `.spx` 空间索引或 `.atx` 属性索引不存在时，查询引擎不会报错，而是自动降级到顺序扫描，同时通过 `QueryResult::fallback_reason` 报告降级原因。

#### 降级路径总览

| 场景 | 空间查询 (Bbox) | 属性查询 | 空间+属性联合 (SpatialWhere) |
|:----|:---------------|:---------|:---------------------------|
| **无 .spx** | 全量顺序几何扫描，原因：`"spatial index missing; sequential model filtering used"` | 无影响 | 路径：`"spatial-where:sequential"`，如果 .atx 存在则使用 |
| **.spx 损坏** | 同上，原因：`".spx exists but could not be parsed; falling back to sequential model filtering"` | 无影响 | 同上 |
| **无 .atx** | 无影响 | 返回空结果，原因：`"attribute index missing"` | 解释：空间候选 + 逐要素 WHERE 评估 |
| **.atx 损坏** | 无影响 | 返回空结果 | 同上，原因：`"attribute index could not be parsed"` |
| **两者都缺失** | 全量顺序扫描 | 空结果 | 路径：`"spatial-where:sequential"`，结果正确 |
| **高覆盖范围（>29%）** | 主动跳过索引，路径：`"bbox:model:sequential-planned"` | 无影响 | 取决于空间候选项密度 |

#### 降级回退的执行流程

**空间查询无 .spx 索引**（`query_engine_geometry.cpp`）：

```
① 检测到 .spx 文件不存在 → spatial_index_present_ = false
② 设置 sequential_fallback = true
③ 执行路径: "bbox:model:sequential-fallback"
④ candidate_count = feature_count（全量）
⑤ 调用 parser_->scan_geometry_blobs() 对所有要素进行顺序几何解码
⑥ 每个几何与查询包围盒进行空间谓词判断
```

**属性查询无 .atx 索引**（`query_engine.cpp`）：

```
① catalog.find_atx() 返回 nullptr
② 返回空 matched_fids，执行路径: "attribute:sequential"
③ 调用者（query_where）收到回退信号，执行全表 WHERE 评估
```

**联合查询无索引**（`query_engine_combined.cpp`）：

```
resolve_attribute_index() 逐项检查：
  ① 字段索引越界 → "attribute field metadata unavailable"
  ② 不支持的操作符（如 Ne）→ "not-equal is not safely indexable"
  ③ 字符串类型不匹配 → "attribute index type mismatch"
  ④ 字符串非 BMP 字符 → "string key is not safely representable by the current .atx decoder"
  ⑤ 数值类型不匹配 → "numeric field encoding is not safely indexable"
  ⑥ 无 .gdbindexes 元数据 → "attribute index metadata missing"
  ⑦ 无 .atx 文件 → "attribute index file missing"
  ⑧ .atx 解析失败 → "attribute index could not be parsed"
  → plan.available = false + plan.reason 传播给调用者
```

#### 主动索引跳过

存在两种故意跳过索引的优化：

**1. 空间查询规划绕过**：当查询窗口覆盖范围超过 `FAST_GDB_SPATIAL_DIRECT_SCAN_COVERAGE`（默认 29%）时，引擎主动跳过空间索引初始化，直接进行顺序扫描。因为在大窗口下，使用索引的开销比顺序扫描更高。

**2. 属性索引绕过**：当空间候选要素数量很少（≤ 65,536 个且 ≤ 总要素数的 1/8）时，跳过 .atx 索引加载，直接对空间候选评估 WHERE 子句。避免加载 .atx 文件的开销。

#### 安全性设计

**核心原则**：索引仅用于缩小候选集，最终语义匹配始终通过完整 WHERE 评估或精确几何空间谓词确认。损坏的索引 **失败关闭**（fail-closed），绝不返回部分结果。

```cpp
// 损坏的 .atx 解析失败 → 不返回任何结果
if (!atx_parser.parse()) {
    result.fallback_reason = "attribute index could not be parsed";
    result.matched_fids.clear();  // 空结果，安全
    return result;
}
```

#### 测试覆盖

`tests/usegdal/test_spatial_where_index_fallback.cpp` 包含专门的降级测试：

| 测试用例 | 场景 |
|:---------|:-----|
| `MissingAtxKeepsCorrectResults` | 移动 .atx 文件，验证结果正确性 |
| `DamagedAtxKeepsCorrectResults` | 用错误数据覆盖 .atx 文件 |
| `InconsistentAtxTrailerCountKeepsCorrectResults` | 损坏 trailer 计数 |
| `CyclicAtxLeafChainKeepsCorrectResults` | 创建自引用叶子页面 |
| `MissingSpxStillUsesAtxCandidates` | 移动 .spx 文件，验证 .atx 仍被使用 |
| `MissingBothIndexesStillMatches` | 移动 .spx 和 .atx，验证顺序扫描结果正确 |

## 第二章 能否融入 GDAL

### 2.1 现有交互方式

目前 fast-gdb 产品和测试以两种方式与 GDAL 交互；另保留一个不构建的历史参考层：

| 方式 | 位置 | 依赖 | 用途 |
|:----|:-----|:----:|:-----|
| **curve_gdal 桥接** | `src/edgar/explorgdb/curve_gdal/` | 可选 | Reader 的线程本地缓存式 GDAL 几何回退 |
| **GDAL 对照与边界测试** | `tests/usegdal/test_*.cpp` | 测试时可选 | 直接调用 GDAL 验证 Reader parity 和写后完整重开合同 |
| **usegdal 参考层** | `src/edgar/usegdal/` | 不进入构建 | 历史 GDAL 包装探索，仅供设计比较，不是产品 API |

CMake 通过 `FAST_GDB_WITH_GDAL` 选项控制 GDAL 依赖：

```cmake
option(FAST_GDB_WITH_GDAL "Build GDAL-dependent components" ON)
```

设置为 `OFF` 时，构建纯 C++ 产品 `fast_gdb_linear`，排除所有 GDAL 相关代码。

### 2.2 三种融入方式分析

#### 方式 A：作为 GDAL 驱动插件（不推荐）

**做法**：实现 `GDALRegister_*()` 函数，将 explorgdb 注册为 GDAL 驱动。

**优点**：
- 对 GDAL 用户透明，可通过 `gdal.Open()` 直接使用
- 可与 GDAL 生态系统无缝集成

**挑战**：
- 需要将 explorgdb 的纯 C++ 解析器封装为 `OGRLayer`、`OGRFeature` 等接口
- **性能优势会被 GDAL 的抽象层抵消**：一旦封装为 OGR 接口，势必要创建 OGRFeature 对象、使用虚函数分发，回到第一章分析的性能瓶颈
- 需要维护 GDAL 版本兼容性（GDAL 的 API 在不同版本间有变化）
- 需要处理 GDAL 的线程安全模型
- 需要处理 GDAL 的编码/坐标系转换机制

**结论**：融入 GDAL 驱动框架后，性能优势将大幅缩水，得不偿失。

#### 方式 B：保持独立库（推荐，当前模式）

**做法**：维持现有架构，explorgdb 作为独立库，通过可选桥接层与 GDAL 协作。

**优势**：
- 纯 C++17 无依赖，可嵌入任何项目
- 性能不受 GDAL 的 OGR 抽象层约束
- 通过 `FAST_GDB_WITH_GDAL` 灵活控制依赖
- 现有 `curve_gdal` 混合架构提供了互操作性
- FileGDB 编辑继续由调用方直接使用 GDAL/OpenFileGDB 完成

**混合架构工作流**：

```
┌─ 查询流程 ──────────────────────────────────────┐
│ ① .spx B+ 树查找（explorgdb）                      │
│ ② 精确几何级过滤（SpatialPredicate）                  │
│ ③ 仅曲线几何/拓扑错误回退到 GDAL（curve_gdal 桥接）    │
└────────────────────────────────────────────────┘

┌─ 外部编辑与读取切换 ───────────────────────────────┐
│ ① 关闭全部 fast-gdb Reader                         │
│ ② 调用方使用 GDAL/OpenFileGDB 独占编辑              │
│ ③ GDALClose 后完整重开 fast-gdb Reader              │
└────────────────────────────────────────────────┘
```

**不足**：
- 无法直接使用 GDAL 的 OGR 工具链
- 需要额外的适配层与 GDAL 生态系统集成

#### 方式 C：为 GDAL 贡献性能补丁（可选补充）

**做法**：将 explorgdb 的优化技术（mmap、零拷贝、B+ 树按需导航）移植到 GDAL 的 OpenFileGDB 驱动。

**优势**：
- 使所有 GDAL 用户受益
- 开源社区贡献

**挑战**：
- GDAL 的跨平台兼容性要求（mmap 在 Windows 上需要特殊处理）
- GDAL 的代码风格和架构约束
- 长期维护成本高
- 零拷贝技术与 GDAL 的 OGR 抽象层本质冲突

**可行范围**：
- 可以为 GDAL 贡献 B+ 树按需导航优化（不破坏 OGR 抽象层）
- 可以为 GDAL 贡献 mmap 选项（GDAL 的 VSI 层已有部分支持）
- 全量零拷贝需要 GDAL 修改 OGR 抽象层，不现实

### 2.3 推荐方案

| 维度 | 方案 A：驱动插件 | 方案 B：独立库 | 方案 C：贡献补丁 |
|:----|:---------------:|:-------------:|:---------------:|
| 性能保持 | ❌ 被 GDAL 抽象层抵消 | ✅ 完全保持 | ⚠️ 部分可行 |
| 维护成本 | 高 | 低 | 高 |
| 生态集成 | 好 | 需要适配层 | 好 |
| 开发自由度 | 低 | 高 | 低 |
| 推荐度 | ❌ | ✅ **推荐** | ⚠️ 可选补充 |

**最终建议**：

1. **主要策略**：保持独立库模式，通过 `FAST_GDB_WITH_GDAL` 控制互操作性
2. **补充策略**：视社区反馈，将部分优化（如 B+ 树按需导航）贡献给 GDAL 上游
3. **长期策略**：如果 GDAL 未来修改 OGR 抽象层（如支持零拷贝读取），可重新评估融入方案

## 第三章 编码与跨平台：中文问题

### 3.1 FileGDB 格式的编码体系

ESRI File Geodatabase 使用混合编码策略：

| 存储位置 | 编码 | 示例 |
|:---------|:----|:-----|
| 字段名（FieldDescriptor.name） | UTF-16LE | 字段名"人口"存储为 `\x4E\xBA\xE5\x8F\xA3` |
| 字段别名（FieldDescriptor.alias） | UTF-16LE | 别名"总人口"存储为 UTF-16LE |
| 空间参考 WKT | UTF-16LE | 坐标系描述字符串 |
| 索引名/列名（IndexEntry） | UTF-16LE | 索引名"idx_名称" |
| 字符串字段值 | UTF-8（Varuint 长度前缀） | 属性值"成都"存储为 UTF-8 字节 |
| XML 字段值 | UTF-8（Varuint 长度前缀） | 元数据 XML |
| .atx 索引字符串值 | UTF-16LE 空格填充 | 固定宽度，右补空格 |

### 3.2 当前编码支持

#### 核心转换模块

**`src/edgar/explorgdb/common/utf16.h` / `utf16.cpp`**

```cpp
namespace explorgdb {

// UTF-16LE 字节 → UTF-8 字符串
std::string utf16le_to_utf8(const uint8_t* utf16_bytes, size_t char_count);

// UTF-8 字符串 → UTF-16 代码单元
std::vector<uint16_t> utf8_to_utf16(const std::string& utf8_str);

}
```

- 支持 BMP 字符（U+0000 ~ U+FFFF），即 1-3 字节 UTF-8 序列
- 不支持 surrogate pair（4 字节 UTF-8 序列，对应 U+10000+）
- 使用 `reserve(char_count * 3)` 预分配缓冲区

#### 查询引擎中的 UTF-8 处理

**`src/edgar/explorgdb/reader/gdb_attribute_index_query.cpp`**

```cpp
// 确定 UTF-8 序列字节长度

// 截断查询字符串以适配 .atx 索引的 UTF-16 容量

```

**`src/edgar/explorgdb/reader/query_engine_combined.cpp`**

### 3.3 中文问题逐项分析

| 场景 | 是否支持 | 说明 |
|:-----|:--------:|:-----|
| 中文字段名（如"人口"） | ✅ **完全支持** | UTF-16LE → UTF-8 转换，BMP 范围内 |
| 中文属性值（如"成都"） | ✅ **完全支持** | UTF-8 存储，直接透明处理 |
| 中文路径（如"数据.gdb"） | ✅ **完全支持** | `fast_gdb_open_utf8()` 处理，Windows 上转 UTF-16 |
| 中文 .atx 索引查询 | ✅ **完全支持** | 经过 `utf8_sequence_bytes()` 和 `truncate_index_string()` 正确处理 |
| 中文 .atx 索引构建 | ✅ **完全支持** | `utf8_to_utf16()` 将中文转为 UTF-16LE |
| 简繁体中文 | ✅ **完全支持** | 均在 BMP 范围内（U+4E00~U+9FFF, U+3400~U+4DBF 等） |
| 日文/韩文 CJK | ✅ **完全支持** | BMP 范围内 |
| 非 BMP 字符（emoji、𠀀等） | ⚠️ **有限支持** | 不支持 surrogate pair，回退到全表扫描 |
| GBK/GB2312 编码输入 | ❌ **不支持** | 只接受 UTF-8 输入 |

### 3.5 建议改进

#### 优先级 1：补充 surrogate pair 支持

当前 `utf16le_to_utf8()` 和 `utf8_to_utf16()` 不支持代理对。这意味着：

- 4 字节 UTF-8 字符（如 emoji 😀、生僻字 𠀀）无法正确转换
- `string_index_key_supported()` 返回 false，导致 .atx 索引查询回退到全表扫描

**工作量评估**：约 2-3 天，包括：
- 修改 `utf16.cpp` 检测并处理 surrogate pair（U+D800~U+DFFF）
- 修改 `utf8_to_utf16()` 支持 4 字节 UTF-8 序列 → 代理对
- 补充测试用例

#### 优先级 2：完成跨平台 CI 验证

GitHub Actions 当前终止于 checkout 阶段，未实际运行。

**工作量评估**：约 3-5 天，包括：
- 修复 GitHub Actions 配置
- 配置 Windows/Linux 构建环境（GDAL 安装）
- 运行 Release 构建 + CTest
- 验证 package consumer 构建

#### 优先级 3：测试 GBK 编码输入行为

当前代码库接受 UTF-8 输入。如果用户传入 GBK 编码的路径或字符串：

- 路径：`fast_gdb_open_utf8()` 的 `MultiByteToWideChar(CP_UTF8)` 会失败，然后回退到 `CP_ACP`
- 建议：在文档中明确声明 UTF-8 输入要求，或在 API 层添加编码检测

### 3.6 总结

| 问题 | 结论 |
|:-----|:-----|
| 中文支持 | BMP 范围内的中文（简/繁）完全支持，有测试覆盖 |
| 非 BMP 字符 | 不支持 surrogate pair，索引查询回退到全表扫描 |
| 跨平台 | POSIX 完整，Windows 有兼容层，CI 未验证 |
| 编码输入 | 只接受 UTF-8，不接受 GBK/GB2312 |
| 主要改进方向 | ① surrogate pair 支持 ② 跨平台 CI ③ 编码输入文档化 |
