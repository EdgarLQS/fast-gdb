# 性能基准与优化历程

**测试日期**：2026-06-16  
**测试环境**：macOS (Apple Silicon)  
**GDAL 版本**：3.9.3 (OpenFileGDB 驱动)  
**数据模型**：Polygon + 4 属性字段（population:Integer64, name:String, category:String, area:Float64）  
**测试规模**：1K / 10K / 100K / 1M / **10M**（5 个级别）

> 本文数字是 2026-06-16 的受控合成数据基线，不能直接外推到 35GB、5 亿对象或高复杂度面数据。真实生产场景必须拆分记录源数据打开/定位、几何解析、目标写入、索引构建和结果验证耗时。

## 1. 当前性能基线

### 1.1 写入性能对比

| 方案 | 1K (us/要素) | 10K (us/要素) | 100K (us/要素) | 1M (us/要素) |
|------|:----------:|:-----------:|:------------:|:----------:|
| GDAL CreateFeature | 8.34 | 4.61 | 4.61 | — |
| GdbBatchWriter (batch=1000) | 4.62 | 4.50 | 4.45 | — |
| **GdbTableWriter 二进制直写** | 40.78 | 7.36 | **4.52** | **4.26** |

**关键发现**：
- **写入速度基本一致**：GDAL、BatchWriter、GdbTableWriter 在 100K+ 规模下均为 ~4.5 us/要素
- **1K 规模时 Writer 较慢**（40.78 us/要素）：因 mmap 初始化和文件预分配的固定开销
- **索引创建开销**：空间索引 ~265ms，属性索引（3字段）~627ms，全索引 ~891ms（100K 规模）
- **索引磁盘开销**：约占数据大小的 80%（空间索引 ~42%，属性索引 ~37%）

这些结果只说明组件在受控数据上的吞吐和查询特征，不证明单对象编辑一定是常数时间，也不证明大 GDB 的追加耗时主要来自索引。单对象操作异常变慢时，应优先检查源图层是否发生全表扫描、目标 GDB 初始化/锁等待或索引刷新。

### 1.2 顺序读取对比

| 规模 | GDAL (ms) | explorgdb per-record (ms) | **explorgdb seq scan (ms)** | seq scan vs GDAL |

| 规模 | GDAL (us) | per-record (us) | **seq scan (us)** |
|:----:|:---------:|:---------------:|:-----------------:|
| 100K | 1.24 | 6.66 | **0.11** |

**零拷贝 sequential_scan 优化原理**：
- 消除 per-record memcpy（直接读 mmap 内存）

> **seq scan 不仅追平了 GDAL，在批量全表扫描场景下反超 9~12 倍。** 这是目前 explorgdb 最快的读取方式。

## 3. 性能优化历程

### 3.1 v7 B+树按需导航优化（2026-06-08 ~ 06-09）✅

**架构变更**：
```
变更前: parse() → 全量加载 all_entries_ (37M entries, ~1.2GB) → 数组 lower_bound
变更后: parse() → 只读 trailer (22 bytes) → query_bbox() → B+ 树按需页面读取 + LRU cache
```

**关键设计决策**：
- `.spx` 页面布局：next_page_id(4) + entry_count(4) + FIDs(N×4@offset 12) + values(N×8@offset 1372)
- 值数组固定偏移：`values_offset_ = 12 + max_per_page * 4 = 1372`（mpp=340）
- 64 位编码：grid_level(2bit) | cell_x(31bit) | cell_y(31bit)
- LRU page cache: 4 slots（每个 tree depth 一个）

**已解决的问题**：

1. **叶子页面链表无限跟随（10M 挂起根因）**
   - 现象: Point 查询访问 2187 万次页面读取，耗时 8.7s
   - 根因: `depth==1` 时跟随 `next_page_id` 链表，但链表跨越所有叶子页面
   - 修复: 移除叶子链表跟随逻辑

2. **编码值范围过滤不精确**
   - 现象: 所有查询场景返回相同 FID 数量（~6.2 万）
   - 根因: `[start_raw, end_raw]` 的二分查找只保证 cell_x 在范围内
   - 修复: 叶子页面遍历时解码 cell_y 进行二次过滤

3. **1M/10M 数据崩溃 (exit 134, SIGABRT)**
   - 根因: `GdbTableParser::load_file()` 将整个 .gdbtable 加载到内存 → OOM；`children[340]` 栈缓冲区溢出
   - 修复: 改为按需读取 `open() + pread() + row_buffer_`；`children[340]` → `children[342]`

### 3.2 预计算倒数优化（2026-06-10）✅

**优化内容**:
- 在构造函数中预计算 `inv_xyscale_`, `inv_zscale_`, `inv_mscale_`
- MultiPoint/Polyline/Polygon 坐标解码从 `raw / scale` 改为 `raw * inv_scale`

**效果**（小结果集场景）:
- Point 查询: 15.4ms → **7.5ms**（**-51%**）
- 大结果集场景变化不大（±3%），瓶颈在 q_bbox

### 3.3 LRU cache 扩展优化（4 → 16 slot）✅

**优化内容**:
- 每层 tree depth 从 1 个 slot 扩展到 4 个 slot
- 总缓存从 4 slot (16KB) 扩展到 16 slot (64KB)

**效果**（小结果集场景）:
- Point 查询: 18.0ms → **11.8ms**（**-34%**）
- peek_blob: 15.8ms → **9.7ms**（**-39%**）

### 3.4 Bitset 去重优化（q_bbox）✅

**优化内容**:
- 将 `std::sort + std::unique` 替换为 bitset 去重 + 排序
- 必须保持排序以维持空间局部性（否则 peek_blob 性能回退 7 倍）

**效果**（Large 场景）:
- q_bbox: 659ms → **322ms**（**-51%**）
- total: 1332ms → **987ms**（**-26%**）

**关键发现**:
- Bitset 去重必须配合排序，否则会破坏空间局部性
- 无序访问 → mmap 预取失效 → peek_blob 性能回退 7 倍
- 有序访问 → 恢复空间局部性 → peek_blob 性能正常

### 3.5 Phase 1-3 优化（基线优化）✅

**优化内容**:
- Phase 1.1: UTF-16 转换添加 `reserve(char_count * 3)`
- Phase 1.2: 字符串字段预分配 `string s(len, '\0')` (2处)
- Phase 1.3: UUID 使用固定缓冲区 `char uuid_buf[33]` (2处)
- Phase 2.1: `field_values.reserve(fields_.size())` (2处)
- Phase 3.1-3.3: WKT 组装预计算长度 `reserve()` (3处)

### 3.6 mmap 优化 ✅

**优化内容**: 
- 在 `gdb_table.cpp` 中添加 mmap 映射
- `read_at()` 优先使用 memcpy，失败时降级到 pread
- `madvise(MADV_SEQUENTIAL)` 提示内核顺序访问

**效果**:
- peek_blob: 5000ms → **160ms**（**31x 提升**）
- 总查询: 6121ms → **1200ms**（**5x 提升**）

### 3.7 Phase C 直写器优化（2026-06-15）✅

**模块结构**：
```
src/edgar/explorgdb/writer/
├── varint_encoder.h         // 零分配 varint 编码（纯头文件，inline）
├── row_buffer.h             // 可复用行缓冲区（零堆分配）

```

**Phase A vs Phase C 完整对比**：

| 规模 | Phase A (ms) | A·us/feat | Phase C (ms) | C·us/feat | 加速比 |
|------|-------------|-----------|-------------|-----------|--------|
| 1K | 7.0 | 7.0 | 0.2 | **0.19** | **36.2x** |
| 10K | 54.5 | 5.5 | 1.9 | **0.19** | **28.7x** |
| 100K | 544.5 | 5.4 | 17.8 | **0.18** | **30.3x** |

**关键成果**：
- **加速 28~36 倍**：每要素从 5.4~7.0 us 降到 0.18~0.19 us
- **瓶颈突破**：完全绕开 GDAL CreateFeature()（Phase A 中占 47.7% 的主瓶颈）
- **零堆分配**：RowBuffer 复用内部 buffer，跨行无 malloc/free
- **混合刷盘**：5000 行 OR 16MB 缓冲，先到先刷

## 4. 性能对比根因分析

### 4.1 基准数据（10M 数据集，817 万结果，Large 场景）

| 路径 | 总耗时 | 加载 | 索引查询 | 记录获取 |
|------|-------:|-----:|--------:|--------:|
| **explorgdb (mmap)** | **1,366 ms** | 29.8ms | 656ms | 207ms (peek) + 185ms (bbox) |
| **GDAL component** | 10,923 ms | 0.6ms | 0.2ms | **10,922ms** |
| **加速比** | **8.0×** | — | — | **52.8×** |

### 4.2 根因 1: I/O 系统调用 — mmap vs pread

| 指标 | explorgdb | GDAL component |
|------|-----------|----------------|
| I/O 方式 | `mmap()` + `memcpy()` | `pread()` 每次读 4~140 字节 |
| Large_10M 系统调用次数 | **0 次** (mmap 一次映射) | **16.3M 次** (8.17M × 2 次 peek) |
| 单次 peek 耗时 | 0.025 μs | 1.34 μs |
| **每特征 I/O 差距** | — | **53×** |

`pread()` 每次调用经历：用户态 → 内核态 → VFS 层 → 文件系统层 → 块设备层 → 用户态。即使有 page cache，每次调用的固定开销约 0.3μs，16.3M 次累计 **~5000ms**。

`mmap` 将文件映射到虚拟地址空间后，读取变为普通内存访问（`memcpy`），由内核按需调页，无用户态/内核态切换。

### 4.3 根因 2: 对象创建开销 — 零分配 vs 每特征分配

```
GDAL component 每个特征的获取路径:
  GetNextFeature()
    → new OGRFeature            (堆分配 ~100ns)
    → 读取 blob 数据             (pread)
    → new OGRGeometry           (堆分配 ~100ns)
    → 设置几何对象到 Feature
    → 返回 Feature 给调用方
    → 调用方销毁 Feature         (堆释放 ~50ns)
  总计: ~250ns 对象开销/特征 × 8.17M = ~2000ms

explorgdb 每个特征的获取路径:
  peek_geometry_blob()
    → 数组查表 feature_offsets_[fid]   (O(1))
    → memcpy 到预分配 row_buffer_      (无分配)
    → 返回指针到内部 buffer
  总计: ~25ns/特征 × 8.17M = ~200ms
```

GDAL 的 `OGRFeature` + `OGRGeometry` 每次创建/销毁涉及多次堆操作。explorgdb 使用单一 `row_buffer_`（只增不减），8M 次调用零次堆分配。

### 4.4 根因 3: 抽象层开销 — 直接解析 vs 虚函数分发

```
GDAL 调用栈（每个特征）:
  OGRLayer::GetNextFeature()        [虚函数]
    → OGRFileGDBLayer::_GetFeature()
      → FGDBLayer::GetFeature()
        → FileGDBAPI::Row::GetFeature()
          → 解码字段值...
  共 5~7 层虚函数/间接调用

explorgdb 调用栈:
  peek_geometry_blob()              [内联]
    → read_at() → memcpy            [内联]
    → BinaryReader 指针偏移          [内联]
  共 1~2 层，全部可内联
```

GDAL 的抽象层设计支持多格式驱动（FileGDB、Shapefile、GeoJSON...），但每个特征都要经过虚函数分发。explorgdb 是 FileGDB 专用解析器，编译期确定所有调用，编译器可完全内联。

### 4.5 根因 4: 索引策略差异 — 空间索引 vs B+ 树

这是 **explorgdb 唯一落后** 的维度：

| 指标 | explorgdb | GDAL component |
|------|-----------|----------------|
| 索引类型 | .spx 网格索引 (线性扫描) | B+ 树 (对数查找) |
| Large_10M 查询耗时 | **656ms** | **0.2ms** |
| 差距 | 慢 3280× | — |

GDAL 的 B+ 树索引查询极快（0.2ms vs 656ms），但被 fetch 的 10922ms 完全淹没。

### 4.6 耗时分布对比

```
                    explorgdb (1,366ms)                    GDAL component (10,923ms)
                 ┌─────────────────────────┐            ┌─────────────────────────────────┐
  加载 (2%)      │ ██                      │            │                                 │
  索引查询 (48%) │ ████████████████        │            │                                 │
  peek (15%)     │ █████                   │            │                                 │
  bbox (14%)     │ ████                    │            │                                 │
  对象创建 (0%)  │                         │  fetch     │ ███████████████████████████████ │
  其他 (21%)     │ ███████                 │  (100%)    │                                 │
                 └─────────────────────────┘            └─────────────────────────────────┘
```

**关键洞察**: GDAL component 的 99.98% 时间花在 fetch 阶段，而 fetch 的瓶颈不是磁盘 I/O（page cache 命中），而是 **CPU 开销**：系统调用 + 堆分配 + 虚函数分发。

### 4.7 性能优势贡献总结

| 维度 | explorgdb 优势来源 | 贡献占比 |
|------|-------------------|---------|
| mmap 消除系统调用 | 16.3M 次 pread → 0 次 | ~50% |
| 零堆分配 | 8.17M 次 OGRFeature 创建 → 0 次 | ~30% |
| 内联 vs 虚函数 | 编译器优化 + 无间接调用 | ~15% |
| 索引策略劣势 | B+ 树 0.2ms vs 网格 656ms | -5% (被 fetch 淹没) |
| **合计** | — | **8.0×** |

简而言之: **GDAL 为每个特征付出了「创建对象 + 系统调用」的固定开销，而 explorgdb 将这两个开销都降到了零。** 当结果集从 1800 增长到 817 万时，固定开销的累积效应使差距从 1× 扩大到 8×。

## 5. 失败实验记录

### 5.1 ❌ 扩大 LRU Cache（16 → 64 slot）

**优化内容**:
- 将 `kCacheSlotsPerLevel` 从 4 增加到 16
- 总缓存从 16 slot (64KB) 扩展到 64 slot (256KB)

**结果**：
- Large 场景: 987ms → 982-990ms（**±0% 无效果**）

**失败原因分析**:
1. **mmap 已优化文件读取** — cache miss 时直接 memcpy，没有 pread 系统调用开销
2. **缓存查找开销增加** — 从 16 个 slot 线性查找到 64 个 slot，抵消了命中率提升
3. **B+ 树瓶颈不在 I/O** — 主要开销在递归调用、二分查找、FID 收集等 CPU 操作

**结论**:
- 已回滚此优化
- **避免重复尝试此方向**

### 5.2 ⚠️ Phase C 系统表未更新

**现象**：
- explorgdb 读回验证：字段解析正确 ✅
- GDAL OpenFileGDB 读取：无法正确读取要素计数 ❌

**根因**：
- `a00000000.gdbtable` 系统表未更新
- 需要实现 `update_system_tables()` 更新系统表

**状态**：⚠️ 待修复

### 5.3 ⚠️ Phase D 自研多层 B+ 树索引

**尝试**：

- AttributeIndexWriter 多类型支持
- GdbIndexesWriter .gdbindexes 元数据

- 多层实现复杂度高

**决策**：

## 7. 混合工作流建议

**最佳实践**：
```
写入阶段：GdbTableWriter 二进制直写（4.5 us/要素，与 GDAL 持平）
    ↓
索引阶段：gdb_index_creator 创建空间 + 属性索引（~900ms / 100K）
    ↓
查询阶段：
  - 属性查询 → explorgdb .atx 索引查询（~1ms vs GDAL ~20ms）
  - 空间查询 → explorgdb .spx 索引查询（~1ms 小范围，~5ms 大范围）
  - 全表扫描 → explorgdb sequential_scan（**0.1 us/要素，比 GDAL 快 9~12x**）
```
